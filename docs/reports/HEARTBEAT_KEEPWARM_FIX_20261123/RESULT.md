### 2.1 包 1：提示、时间、休息、发布门、预计时间

**唤醒提示。** 心跳尾事件现在固定四行：宿主标记加当前时间、三种选择、真实剩余号码、说明正文会直接发给乔乔。

```
[心跳唤醒] 2026-11-24 14:05 Tue UTC+8
醒了。可以直接找乔乔说话，也可以先抽一张，再决定要不要找她；也可以安静结束。
可抽号码：1、2、3。
这一轮的聊天正文会直接发给乔乔。
```

- 时间在本轮准备派发时读取，按 `Asia/Shanghai` 格式化，与普通聊天共用同一个格式函数（从 `modelTimeContextText` 里抽出的 `modelClockText`）。它只进宿主尾事件，不进冻结的 system 前缀；每次心跳得到新的时间，已派发的邀请文本不被改写。
- 与执行稿建议的一处措辞差别：保留了原有的 `[心跳唤醒]` 标记原样，把时间放在同一行后面，没有改成 `[心跳唤醒 · 时间]`。原因是这个标记是稳定的宿主来源标识，聊天界面和多处测试都靠它识别。
- 十张耗尽时的提示同样带上时间，文字未变。

**退役的重复实现。** `8d343b5` 引入的“按上下文是否已有当日完整邀请决定是否重复规则”的查询、`DRAW_RULES` 常量和 `begin()` 的 `windowId`、`retainedMessages` 参数一并删除。调用方只有 `begin()` 自己，对应测试已替换。

**休息状态。** 存在 `conversation_activity` 表的新列里（schema v91：`resting`、`rest_decided_at`、`rest_source`、`rest_message_id`），由 `ConversationActivityService` 读写。

- 触发：`conversation-rest.ts` 的 `detectRestIntent` 只读乔乔本人首次正式接受的输入。它按分句判断：开头或结尾分句里出现睡觉、休息、醒来的明确说法，并且不是对别人说的、不是提问、不是讨论功能、不是否定或以后再说的计划。接入点是既有的消息生命周期钩子，所以文字、语音通话转写、聊天语音条走的是同一个入口。模型回复、工具结果、历史召回、预留留言、编辑和重发都不触发。
- 语音条按宿主已接受的转写判断，不新增转写。
- 休息不是真实消息：不动 50 分钟锚点，不动活动版本。
- 生效范围：调度器不再保留到期目标、领取前复查、执行位内的资格门、运行中每次模型和工具派发前、以及发布前。抽卡轮和十张耗尽后的“回 1”走的是同一个门，资格门在读取牌组之前就结束。
- 恢复：乔乔明确说醒了、早安、回来继续聊，或在心跳页点“恢复心跳”（`POST /api/v1/background/heartbeat/resume`，带操作键，同键重放首次结果）。char说话、午夜、日期变化、08:00 都不会自动恢复。睡前补话、重复晚安、孤立表情不解除。恢复不打开原本关闭的心跳总开关。
- 首次迁移不回放历史：旧行默认“未休息”。

**最终发布门。** 心跳正文真正发往聊天前再读一次当下状态：夜间静默、休息中、总开关关闭，任一成立就不发。覆盖最终正文、工具调用前的正文和“1”。

- 已发出的请求、费用、已交付的牌、已成功的工具动作和已真实发出的消息都保留。
- 被拦的正文不延期补发，不进朋友圈，也不进入下一轮的模型协议历史（模型不会以为自己说过一句她没看到的话）。
- 自主预约和自由活动不受这道门影响，它们继续按各自的合同执行。

**预计时间。** 设置接口如实返回暂停原因：静默期进行中、到点落在静默期、休息中、开关关闭，都不再给出时间。两个页面共用一段文案函数，前端不自己推算。

### 2.2 包 2：留言视图与朋友圈层次

**留言视图。** `GET /api/v1/content/future-notes` 现在由宿主组装：从内容服务读全部留言，按交付账本分到“待用”或“已使用”，再分页。

- 归属只看 `heartbeat_draw_operations`。留言本身不存任何状态，所以旧留言不需要回填，也不存在第二份消费状态。
- 已交付的离开默认列表，在“已使用”视图里仍可编辑、删除；原文、固定修订和账本都不动。移出列表不是删除。
- 投递结果未知的留在待用列表，单独计数为“待确认”，既不算已使用，也不会重新可抽。
- 分页在过滤之后进行，所以各页不重不漏，计数与列表一致。
- 内容服务不可达时返回不可用，不返回空列表。

**朋友圈层次。** 每个块由服务端标明层次：主体是卡面和本轮真实发出的回复，详情是邀请、揭牌、选号、动作和结束状态。页面先显示主体，把详情折叠起来；已成功的业务动作在主体下用一行“还做了：…”列出。旧版没有动作明细的记录照常显示卡面和回复，不补造动作。

### 2.3 包 3：发送说明

`chat_send_text` 的说明改为与实际一致：预约唤醒和自由活动轮的正文不会自动发出，要用工具；普通聊天和心跳轮的回复由宿主自动发出，不要用工具重复同一句。参数和回执未变，升级前冻结的窗口照常可用。

工具目录、信封和会话三份 golden 用既有脚本重建，差异只有这段说明及其定义 ID。

### 2.4 包 4（增量）：聊天里主动抽牌

- 普通聊天回合可以直接调用 `heartbeat_draw`。抽牌的那个回合自己就是一个“逻辑回合”，以回合 ID 记录，与心跳共用当天的固定牌组和消费账本：任何一边抽走的号码两边都不能再抽，一回合约最多成功一张，重试同一个号码拿回第一张，改要另一个号码被拒。
- 交付证据是该回合自己已确认发出的请求。没有新增工具、列或表。
- 读取工具定义（`tool_define` 或 `tool_catalog`）会返回当前剩余号码；牌组未固定时十个号码都可抽，第一次抽牌才固定牌组。因此下午新增的留言仍然进不了上午已固定的牌组。
- 夜间静默、休息和心跳总开关只管自动唤醒，不管她正在进行的聊天。自主预约和自由活动轮拿不到抽牌，直接到达处理函数同样被拒。
- 聊天里抽完十张，只被告知“今天十张牌已经全部抽完”；下一次获准的心跳才按原约定要求回复“1”。
- 聊天里抽到的牌有自己的朋友圈记录：卡面加揭牌之后真实发出的回复。要牌时顺带说的别的、或以这些话开头的气泡，不算对牌的回应。揭牌记录标明属于普通回合，聊天界面不会把这一轮当成心跳轮。
- 升级前冻结的窗口保留原定义文字，读取定义时补一句说明并带出剩余号码。
- 工具目录在普通聊天里多了一行，两个换窗测试夹具的软线按仓内惯例平移了 60 token。

## 6. 已知限制与需要裁定的事项

1. **到点落在静默期的心跳。** 按现行规则，这样的目标在夜里不执行；08:00 之后调度器会领取一次，但那时缓存早已冷了（静默期 9 小时，缓存 1 小时），所以在发出任何模型请求之前就以“缓存已冷”结束，不会有消息。这是原有行为，本次没有改。页面现在如实显示“到点落在静默期，届时暂停”。如果希望早上有一个明确的心跳，那是新的产品规则。
2. **聊天里抽牌时模型先说了别的话。** 如果模型在要牌的同一条消息里先说了别的，抽完再回应，两段会落在同一条气泡里，这条气泡不算对牌的回应，朋友圈只留卡面和动作。模型直接抽牌再回应时，回应会带上。
3. **聊天里不显示卡面。** 与心跳一样，揭牌系统行在聊天里是隐藏的，卡面在朋友圈页看。沿用现状。
4. **回退。** 回到旧版本后，晚安不再暂停心跳，聊天里不能抽牌；已记录的休息状态、牌组和消费事实都保留，再次升级即恢复生效。
