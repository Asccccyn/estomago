## 此次独立复现的问题

### 1. 阻断 · 中途已交付的卡面在重启后的模型上下文消失

触发顺序为抽卡成功、卡面进入模型的下一次请求、模型调用写记忆、记忆 effect 和动作引用提交，然后在调用完成工具前强停临时 Host。这个时点沿用了修复提交自身的故障注入点。复审继续发出一条自然聊天，分别检查发送记录、规范轨迹和模型边界的实际输入。

|观测|API direct|Claude SDK direct|
|---|---|---|
|强停前已确认发送的输入|同 ID 的 draw 调用和含卡面结果各 1 次|已发送请求投影包含卡面，假 SDK 实际接到该次工具结果后才发起写记忆|
|重启后的窗口|原窗口，规范轨迹的 draw 调用/结果均为 0|原窗口，规范轨迹没有卡面；进入 SDK 冷回放|
|下一条自然聊天|发出 1 个请求，调用/结果均为 0|发起 1 次 query；实际 replay 输入和本次请求投影都没有卡面|
|已保留的其他事实|原 provider request 仍有证据；消费和已提交记忆引用保留，恢复期间 0 次补模型|原 provider request 仍有卡面；没有因恢复而重跑该轮|

这使乔乔能看见系统揭过牌，而char重启后接不上刚看过的内容。正常终态的整轮轨迹写在 `apps/host/src/runtime/background-outcome.ts:107`；接受完成工具的恢复路径要求有 completion checkpoint，见 `runtime/completion-recovery.ts:48`。未到完成点时，`modules/heartbeat/runtime.ts:366` 恢复账本和朋友圈，以空 finalMessages 收尾，没有把原请求中已经证实送达的协议恢复给窗口。既有强停测试检查到文章、记忆和无重复派发即结束，这些断言依然成立。

**最小修复与复验**：在现有轨迹／检查点恢复边界按已确认请求、窗口和调用身份保全已派发前缀，按同一身份幂等补齐。已经执行但尚未送回模型的结果独立保留其待派发事实，未知结果保留未知。不得从朋友圈或编辑后的业务源重建已发正文，也不能为补历史重开旧轮。重复重启后，第一次自然聊天应收到原 draw 调用和同 ID 的原卡面各一次，记忆不重写，SDK 冷回放与 API 有相同事实。

### 2. 已确认 · 揭牌前的话会被当成对预留话的回应，再进入免冷却重播池

通过正式 Content 入口创建十条合成预留话。在收到邀请后，模型先通过 chat_send_text 发出“我现在去抽牌”，再选 1 号；收到卡面后的唯一动作是 background_complete(noop)。正式消息的实际顺序为 invite → assistant → card。该轮却被投影成 drawn，真实来源枚举将它列为 first_reserved_response，按该引用解析出的“回应”包含那句揭牌前的聊天。

成因在 `modules/heartbeat/runtime.ts:348` 使用整轮“是否存在任何助手消息”来决定 drawn；`modules/heartbeat/sources.ts:221` 对首次回应重播也取整轮的助手消息。**影响**是明明没有回答这条留言，却产生了一份可重复投递的历史回应。原留言的一次性消费仍然有效。

**最小修复与复验**：在原轮保存符合条件的、实际交付之后的回应引用；重播从这些固定引用读取。至少用两组事件序列验收。只有揭牌前发话时，保留聊天、卡消费和日常映射，重播资格为零。揭牌前后各发一句时，重播只包含后一句及其原修订。

### 3. 已确认 · 合法自设预约成功，朋友圈没有对应动作

在已开启自主预约、有预算的正常心跳里，经实际工具目录调用 wake_manage(schedule)，随后沉默结束。Host 生成 1 个 self_schedule 任务，创建者为 jiaming，模型收到 1 个带 task_id 的成功回执。该篇朋友圈的动作数组只有 selection，读回页面也没有预约。

`modules/wake/module.ts:39` 附近的业务注册未登记预约动作；`capabilities/executor.ts:52` 和 `modules/heartbeat/actions.ts:14` 只采集声明过的动作。因此“不能由用户代设”和“模型自己成功设了要映射”是两个验收点，前者已过。写新星与记忆的成功用例也证明不了所有写动作均已覆盖。

**最小修复与复验**：在预约写入回执边界按 operation 区分建立、改期和取消，关联原任务 ID/修订。list 是读取，不能算设置成功。复验成功、同键重试、list 和失败后沉默，任务数与文章中的动作一致。对其他可改变业务状态的已开放工具按其源回执核对；本条确认的反例是自设预约。

### 4. 已确认 · 关掉客厅候选后，仍有权限的历史卡面变成 forbidden

打开 include_living_room，实际抽中一条客厅来源并确认交付。聊天历史卡面查询先返回 available。通过正式设置接口只关闭“客厅参与抽卡”后，同一张历史卡返回 forbidden，而当前身份在客厅的正式原帖接口仍读到同一 ID、修订和正文。全程为隔离源服务，未更改该帖权限。

`app-context.ts:437` 将候选设置绑定到 adapter.enabled；`modules/heartbeat/sources.ts:167` 在所有 resolve 中使用同一开关。`runtime.ts:303` 的历史展示也经此处。现在正确实现了停用后的未来候选过滤，同时错误影响了过去事实的读取。

**最小修复与复验**：将“允许参与抽卡”用于枚举、认领和派发，将“当前读者能读这个固定修订”留给源端和历史解析器。关闭候选后，未交付的该源号码不可抽，已有卡在真实源权限仍有效时可读；原帖确实撤权、删除或修订不可读时，历史展示如实降级，不从正文副本复活。
