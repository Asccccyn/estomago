# 04｜作品、相册入口与媒体检索执行合同

## 0. 本文件的用途与边界

本文件供 GLM 实施本轮相册功能，承接已经接受的产品方案。拆分与死代码清理的 diff 审计已经完成；本轮从施工第一步即按模块边界接线，每批完成时同步退役被替代的旧路径，不安排“功能先堆起来，最后再专项拆耦合、清死代码”。

本包关于 M 媒体间唯一正本、迁移、对话存档、滚窗图片和通知的其他合同与本文件共同生效。前端保持一个连续聊天窗口；照片和留言接入现有“选定原文＋开窗包”滚入下一模型上下文段的流程。本文件不另行定义数量和消费规则：**每次滚窗带入统一遵守本包 03 的合同与 10 张上限**，作品、精选相册或工具不得绕过。滚窗后的正常聊天发图沿原有规则，不误套用带入限制，也不新增多窗口 UI。

GLM 的汇报是现状线索，不是对当前工作树和运行进程的替代取证。实施前核对现有 `apps/content`、作品面板、相册工具、媒体检索、媒体查看及发送路径的真实调用者，记录最终接入点。接口名称以现仓为准；本文中的职责名称不要求额外新建一组同义工具。

## 1. 开工即明确模块职责

在既有架构内分配职责，不把下列能力写入一个巨型 route、工具分支或全能 service：

| 职责 | 实施位置与约束 |
| --- | --- |
| 媒体对象存储、读取和版本 | 复用 M 媒体间及本包存储合同；M 保存正式字节和作品源内容 |
| 分类、作品、相册条目和留言的业务操作 | 复用已有 `content` 应用能力；持久化归属遵守本包统一裁定，只保留一个可写正本 |
| E 页面展示及模型工具适配 | 通过同一业务服务读写，不让网页、模型各维护一套条目和分类规则 |
| SVG／互动作品制作 | 使用作品模块，负责保存可继续编辑的源版与必要依赖 |
| 图片 API 适配 | 独立适配 OpenAI 请求、结果与状态；不负责相册 UI、原文同步和检索排序 |
| 图片与表情包检索 | 复用现有 Gemma 服务与媒体索引，查询入口统一路由 |
| 对话存档文字检索 | 调用 M 现有 Qwen 与 BM25 基础设施，限定存档内容范围 |

如果某个旧入口仍有真实调用者，先迁移调用者并验证，再删除旧实现。不得以“兼容”为由长期保留旧 E 正式文件库与新 M 正式文件库两套可写路径，也不得新增 `media_search_v2` 等平行能力绕开现有入口。

现有 DTO、服务接口和客户端适配器能复用时直接复用；需要改变引用格式时，集中在适配边界转换，不能在页面、检索器、发送器、开窗组装器中各写一份转换逻辑。

## 2. 四个前端入口及分类规则

E 提供四个清楚的入口。它们是 M 媒体内容的分类展示与业务操作入口，不复制媒体字节。

| 入口 | 展示内容 | 进入方式 | 主要操作 |
| --- | --- | --- | --- |
| 作品 | char制作的 SVG、互动小组件、生成图片 | 制作成功且 M 保存成功后自动进入 | 打开作品、查看源版、继续编辑、按用途加入其他分类 |
| 我们的相册 | 双方主动精选的重要照片和对应留言 | 从聊天、M 媒体间或已有作品中明确选入 | 看照片、读留言、调整分类与开窗策略 |
| 对话存档 | 按用户或char明确选择的对话范围保存的记录 | 调用同一存档业务能力 | 按争吵／甜蜜分类查看、检索、打开原存档 |
| 表情包 | 用户上传供char使用的素材，以及明确加入此分类的自制素材 | 上传为表情包，或把已有作品明确归入 | 检索、预览、发送真实附件 |

具体要求：

1. 现有“作品”面板及 `content` 中的 creations、albums、entries 能力继续使用。补齐其余入口的人类 UI，不另起一套相册后端。
2. 同一对象可以出现在多个入口。例如一张char生成的水獭图可以同时属于“作品”和“表情包”；这只新增分类关系，不重复上传文件，不生成新的假副本。
3. “我们的相册”是精选集合。聊天中发送过的全部图片自动归档到 M 媒体间，不自动全部进入精选相册，也不自动开启开窗注入。
4. M 媒体间能汇总查看所有已正式保存的照片、表情包、对话存档和作品，并能显示正确类型及相关来源。原文中的图片应可直接查看，而不是只显示“此处有附件”。
5. 实际发出的聊天图片与附件应建立原文关联。未发送草稿不得被冒充为已发送聊天原文；独立上传到相册或表情包的素材可以存在于媒体间，但不得伪造一条聊天消息作为来源。
6. 用户和char对同一条目的操作走同一服务、同一权限检查与同一幂等语义。不得出现人类 UI 能看到一套相册、模型工具看到另一套相册。
7. “仅收藏／下次滚窗一次／每次滚窗”的设置入口统一调用 03 文件规定的业务能力，接在既有滚窗链上。不得靠前端直接改一个布尔值绕过容量检查、段内版本冻结及实际投递回执。网页刷新、重新打开或重连不算滚窗。
8. 从某个相册移出、取消表情包资格、取消开窗带入，都只是改变对应关系。删除 M 正式对象必须遵循全引用检查，不能由某个页面独自决定删除字节。

## 3. 作品的保存、打开与继续编辑

### 3.1 保存的是完整作品

作品制作完成后，必须保存可被再次打开和继续编辑的原始内容：

- SVG：保存真实 SVG 源文件；保留矢量结构，不用 PNG 截图替代。
- 互动小组件：保存现有作品运行器支持的源文件、入口与必要资源关系。若作品依赖图片等本地资源，以 M 媒体引用或完整作品包中的受管资源解析；不能只保存一个临时开发地址。
- API 生成图片：保存 API 返回的真实图片字节；原格式和透明度按实际结果保留。不得用响应预览图代替原图，也不得把暂时可用的供应商 URL 当作已完成存档。
- 若既有图片编辑能力在本次受影响范围内：保存编辑结果，并保留它与输入图片、上一个作品版本的关系；不把重新生成一张近似图宣称为原作品源版编辑。本包不额外要求新建一套图片编辑器；SVG/小组件的已有制作与源版继续编辑能力仍须保留。

缩略图、搜索预览和渲染图属于派生内容，可以按现有策略生成和重建；它们不能替代源版，也不能作为源版丢失时的“已经完整保存”证据。

### 3.2 稳定引用与版本

对外引用采用本包约定的稳定媒体／作品引用。哈希用于对象去重和完整性校验；若既有 M 合同将其作为稳定媒体身份，遵守 02 的受管引用规则，不额外制造一套 ID。临时读取 URL 只用于一次取回或展示，不作为作品的唯一身份。

继续编辑已有作品时，应能定位具体作品和当前源版，读取源内容并提交新版本。保存新版本必须遵循现有并发修改保护，不能覆盖另一方刚保存的版本。历史聊天、既有存档或已冻结开窗资料引用哪个版本，应遵守各自合同，不因作品列表默认展示最新版而悄悄替换历史内容。

M 正式保存成功后才把作品标记为“已保存”。E 可以显示制作中或保存中的状态，但不能提前返回“已收入作品集”或发布一个打不开的永久引用。

### 3.3 互动作品的运行边界

复用现有隔离作品运行器。作品源码不能直接插入宿主页面执行，也不能获得 E/M 登录凭据、图片生成 Key 或任意宿主工具权限。源码、依赖清单和运行入口需要一起验证能打开；只验证一个截图可见不算互动作品验收通过。

如果当前作品能力只支持 SVG 或静态 HTML，先如实核对已支持格式，补齐本次要求的必要运行能力。不得把不支持的交互包退化成截图并宣称交付。

## 4. OpenAI 图片生成接入

### 4.1 型号与配置

本轮已核实的 API 型号为 `gpt-image-2.6-flare`、`gpt-image-2.6-sunburst`。在后端图片供应商配置中选择实际使用型号，不把前端展示名 `image2.6` 直接当请求中的 model ID。

Key 由用户随后在 E 的后端设置中配置，复用现有凭据保存和业务权限体系。模型工具只得到“是否已配置、是否可执行”的必要状态；Key 不进入工具参数示例、生成提示词、相册条目、客户端 bundle、日志或作品源码。

未配置 Key 时：

- 相关入口清楚显示尚未配置；
- 请求返回明确的配置缺失状态；
- 不创建假的成功图片、不返回虚构媒体引用、不自动切换其他供应商或其他 Key。

付费联调遵守当前执行会话已经存在的授权；本包不额外扩大调用次数或费用范围，已有明确授权也不需重复询问。尚无 Key 或相应授权时，代码与错误路径可使用隔离的供应商响应夹具验证，但夹具只能存在于测试环境，不能进入正式相册或被标记为真实生成结果；真实远端验收明确列为待验证/阻断。正常业务生图沿用用户已设置的业务权限，不新增一套与现有权限冲突的确认机制。

### 4.2 生成和入库分开恢复

实现必须区分“供应商生成”与“把生成结果存入 M”两个阶段：

1. 接收制作请求，使用既有业务操作身份防止客户端重发、工具重试重复启动同一请求。
2. 调用供应商并取得可验证的真实结果。
3. 及时取得完整图片字节，按本包存储合同写入 M。
4. M 正式保存成功后，建立作品条目与必要来源关系，返回可打开的稳定引用。

**如果第 3 或第 4 步失败，重试保存和关系提交，不能再次调用付费生图接口。**保留恢复所需的供应商请求身份、结果状态及临时字节；临时文件遵守本包上传暂存和清理规则，不成为 E 的第二份正式媒体库。

供应商超时但生成结果未知时，不能假定没有执行并无条件重发。按实际 API 提供的查询或恢复机制核对结果；没有可靠恢复能力时，保留“结果待确认／生成结果未取得”的真实状态，不用循环重试造成多次计费。供应商明确拒绝、配置错误、取图失败与 M 保存失败应有不同的可诊断状态。

所有恢复行为在现有任务／操作恢复机制内实现，不因图片生成另建一个与现有消费者互不知情的后台调度体系。

## 5. 自制表情包与普通作品的关系

图片生成或 SVG 制作完成后默认进入“作品”。用户或char明确选择“加入表情包”时，再创建表情包分类关系。

加入前核对该对象是否可被当前消息附件协议按表情包发送。互动 HTML 不能因为属于作品就自动作为图片附件发送；如需从它制作表情包，必须有真实生成且入库的可发送媒体对象，并保留来源关系。不能把互动作品链接伪装成表情包图片。

用户直接上传的表情包保留原始文件能力；例如支持的动图应保留动画，不能在无提示情况下只存第一帧。预览、索引可以按现有能力使用派生图，但发送使用正式对象。

重复发送同一个表情包只新增消息引用。再次加入分类、跨相册收藏都不重复存储同一份文件。

## 6. 统一媒体查询入口

### 6.1 范围必须明确

优先扩展现有 `media_search` 或相应媒体查询服务，通过明确 scope 路由到作品、精选相册、对话存档、表情包或完整媒体间。具体枚举名称沿用项目命名规范，不要求照抄本文中文名称。

既有调用的默认含义不得无意改变。新表情包入口必须明确限定表情包 scope；精选相册查询只看精选集合。完整媒体间查询应是明确的查询范围，不能把它作为表情包无结果时的隐形补查范围。

表情包查询不得因向量相似而返回用户自拍、未归入表情包的私人照片或争吵截图。先应用身份、分类、可用状态与发送资格约束，再检索和排序；最终发送时仍检查对象引用及发送能力。

### 6.2 模型分工

| 内容 | 复用能力 | 不允许的实现 |
| --- | --- | --- |
| 图片、照片、表情包 | 现有 EmbeddingGemma 2 文本／图片向量检索，结合已有标题和说明 | 新建一个让 Gemma 生成虚构文件和 URL 的聊天代理 |
| 对话存档 | M 现有 Qwen3-Embedding-4B 与 BM25 检索基础设施，限定存档内容类型 | 在 E 再加载一份千问；把存档混入所有普通记忆召回 |
| SVG、互动作品 | 标题、说明、作品类型；必要时复用可用的预览向量 | 只索引和返回截图，丢弃实际作品引用与源版 |

Gemma 与 Qwen 的向量空间不能直接混合计算相似度。若统一展示跨类型结果，应在各自查询完成后按有定义的融合规则处理，不能直接比较两个模型的原始 cosine 分数。不得为满足本轮功能重构已稳定的普通记忆召回策略。

### 6.3 标题、说明与文字信息

上传或存档时允许附加简短标题和说明；这些字段是可选项，没有说明也能保存和检索。char亲自留下的话必须原样保留其身份与内容，不能被索引摘要覆盖。

中文表情包如果已有 OCR 或文字提取能力，可复用提取结果帮助检索；人工标题与说明仍可修正。不得假称 embedding 模型已可靠读出全部图片文字，也不能为了本轮需求默默新增一个 OCR 模型常驻进程。

当前没有 OCR 时，可以交付已经明确支持的图文向量、标题和说明查询，并如实标记文字提取未提供；不得把 OCR 错误吞掉后把该结果当作完整文字检索成功。

对话存档直接利用选定原文的文字建立索引，不重新识别聊天截图。服务端读取已保存消息进行索引，不等于让char重新读一遍上下文。长存档沿用现有文本分段基础设施，并保留匹配片段回到原存档的精确定位。

## 7. “没有合适结果”是正式业务结果

向量最近邻即使没有合适内容，也可能给出一个相对最接近的对象。因此不能把 top-1 无条件当作命中。

实现应支持基于实际素材校准的接受／拒绝条件，结合查询范围、语义相关性和已有文字信息。不预设没有依据的统一阈值，不把相似度乘以 100 当成“正确概率”，也不要求所有类别共用一条未经验证的阈值。

使用一组小规模、可解释的真实素材与查询样例验证：正向命中、明显不相关、相近动作但含义不同、相同角色但语气相反，以及已有文字说明或已启用文字提取能力所覆盖的中文样例。OCR 不是本轮新增必做能力；未启用时记录实际能力边界，相关不确定查询允许返回无合格匹配，不能伪装已经完成文字识别。样例与判断依据写入本轮验收记录，避免为了提高命中率牺牲“没有就没有”。

至少区分以下结果语义，实际字段名称可适配现有合同：

| 状态 | 含义 | 模型或前端应知道的内容 |
| --- | --- | --- |
| matches | 查询正常完成，存在合格真实对象 | 少量结果及可继续操作的真实引用 |
| no_match | 查询正常完成，没有合格候选 | 没找到合适的内容 |
| unavailable | 服务忙、503、连接失败或运行故障 | 本次暂时无法检索，不能声称库中没有 |
| pending_index | 请求涉及的素材尚未完成索引 | 尚未完成索引；如已持有明确引用，可按引用读取 |

素材已入库但索引尚未完成时，网页仍能按分类和直接引用查看。不要把检索补索引失败扩大成媒体保存失败；也不要把“任务已排队”当作“已经可搜到”。队列、退避与服务 release 化复用本包部署合同及既有能力，不能通过并发无上限重试掩盖 503。

## 8. 模型返回面与真实发送

查询结果保持精简：默认给一个最合适的结果；确有必要时给少量候选。返回稳定引用、必要的短标题／说明及有用预览；对存档可带日期、分类和有限匹配摘录。不额外附带向量、内部校验哈希、存储路径、队列状态历史、供应商响应全文和调试评分；若既有稳定媒体引用本身以 hash 标识对象，允许按受管引用合同返回这项必要身份，不新增平行资产身份，也不让模型自行猜测 hash。

精简不等于切断后续操作。每项命中必须有可用的进一步读取入口：

- 图片可取回真实图片；
- 作品可打开真实作品，按权限读取和继续编辑源版；
- 存档可查看准确的存档正文及其来源；
- 表情包可通过现有消息发送能力发送真实附件。

发送端接受已存在的受管媒体引用，并由系统解析附件字节。禁止让模型自行拼出静态 URL、猜测 hash、构造本地文件路径后直接发送。前端必须渲染图片／表情包附件，不能只显示一段 Markdown 链接并报告“表情包已发送”。

检索与发送是不同动作：搜索结果不自动变成一条对用户发送的消息。char在当前业务权限下选择发送后，再由统一消息服务完成发布与原文关联。发送失败应返回真实失败，不能仅凭搜索工具找到了素材就通知用户发送成功。

## 9. 迁移后的索引和引用连续性

字节正本迁移到 M 后，查询、预览、进一步读取及发送都应能从 M 引用解析文件。原 E asset ID 仅按本包迁移合同作必要的存量映射，不能继续承担第二份字节正本的身份。

对象字节、embedding 模型与预处理指纹未变时，可以复用现有向量，更新对象解析关系；不要求仅因存储位置变化就把全库重新嵌入。若模型或预处理指纹发生改变，按现有索引版本机制处理，不混用不同版本结果。

检查现有扫描器、补索引消费者和清理逻辑：E 文件迁出不得被误判为素材已删除，继而清空仍由 M 保存的有效索引。分类变化应更新查询过滤；取消表情包资格后，素材仍可在其余合法分类中存在。

## 10. 本模块的交付与验收

本模块完成的判断必须覆盖真实业务链路，而非仅检查路由返回 200：

1. E 四个入口连接已有业务后端；同一分类和留言在人类 UI、模型查询、M 媒体间的相关展示中一致。
2. 一张正式聊天图片自动归档到 M；选入“我们的相册”后只增加分类关系。移出精选相册后，聊天原文和 M 图片仍可读取。
3. 一份 SVG／互动作品在 M 保存完整源版，可打开、可再次编辑并保留历史引用；验收不能用一张截图代替互动操作。
4. 一个已有作品明确归入表情包后可检索和发送；未归入的自拍不得进入表情包候选。
5. Key 缺失返回未配置。供应商生成成功而 M 保存失败的测试证明：恢复只重试存储，不再次调用生成供应商。未授权付费测试不得执行。
6. 表情包检索验证合适命中与合理拒绝；服务故障、索引未完成和正常无命中呈现不同状态。
7. 对话存档查询调用 M 已有文本检索能力；无说明的存档仍能定位；查询先返回少量信息，并能进一步打开正确正文。
8. 检索得到的引用可以在真实发送路径成为附件，不依赖 E 已退役的正式文件路径，也不依赖过期供应商链接。
9. 同一批改动中，替代路径的真实调用者已迁移，重复路由、旧解析逻辑和失效扫描逻辑同步退役。记录仍保留的兼容适配及其真实消费者，不留下“以后再清理”的双写架构。

允许复用已有测试夹具及少量针对故障边界的验证。不要为每个字段编写镜像测试，不进行大规模重复生图、全库反复重嵌入或无界文件夹具生成。与本包其他模块共享验收证据，避免同一业务路径重复搭建多套测试框架。
