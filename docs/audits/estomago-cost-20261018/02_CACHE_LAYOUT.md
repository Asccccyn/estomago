**任务书 3.2 三个候选问题逐一核验：**

- **问题 A（时间信息插入过早）：不存在。** 时间上下文（time/context.ts）每轮刷新后拼进**尾部 user 消息**（assembleContext allowlist=time_context+user_input 两段），不进 system 前缀；112 笔的 A 段 hash 零变化（见下表）。
- **问题 B（工具定义每轮重排序）：不存在。** 顺序=数组字面量固定；`frozenToolsByWindow` 同窗定格（词表中途变化不改变本窗 tools）；指纹期内 tools_hash 仅 2 次变化，均有真实代码变更对应。
- **问题 C（Mariposa 快照每轮无意义变化）：不存在。** B 段 hash 全程零变化；bootstrap 完整成功才进进程缓存（`bootstrapByWindow`）。

## 4. 一次性整段重建的定性（$0.953375，10-17 20:18 UTC）

read=0、write=94,961 的唯一一笔。前因：c85c964 部署后服务重启，工具 24→37 项——tools 位于前缀最前段，工具集真实变化使后续整段缓存必然重建。**定性：部署成本，非缺陷。** 同版本后续两笔（$0.0524/$0.0524）证明重建后立即恢复满复用。把 37 项退回 24 项省这笔钱违背"不删工具能力"约束，不做。

附带识别的机制限制（不修，留档）：工具冻结快照仅存进程 Map，重启后由 `buildHostTools()` 现算重建。若重启时工具定义与重启前一致（绝大多数情况），前缀照常衔接；仅当"运行中工具代码/词表已变 + 重启"才触发一次整段重写。心情词表（mariposa mood vocab）变化会使 memory_hold 枚举变化——同窗内被冻结快照挡住不破缓存，跨重启则并入上述一次性重建。触发条件=她改词表+重启，频率极低，不为此引入持久化冻结状态。
