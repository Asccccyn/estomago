## 0. 本次究竟改什么

本文替代 `estomago_Mariposa_OR_1h_lifecycle_GLM_v0.2_2026-10-05.md` 及更早的上下文方案，作为本任务的完整施工口径。旧文件保留为历史证据，不能同时执行冲突条款。

本次用户明确选择的是：

> 原文自动保存。主模型自行决定哪些事情要 hold，也有不 hold 的权利。没有 hold 的对话不是默认漏记，不需要小模型查漏，不需要全部补成桶。临近自动换窗时，宿主递一次提醒，重点检查最近一次成功 hold 书签之后的对话；主模型可以选择零新增 hold，然后直接换窗。

因此删除 v0.2 中以下要求，不得换个名字保留：

- 每个普通聊天回合都必须返回记忆处理决定。
- 没有 hold/处理回执的每一段原文，自动形成“待补齐记忆”任务。
- 换窗前遍历并补齐全部未绑定、未 hold 或未分类的历史。
- 为纯闲聊创建未完成事件状态，目的只是防止它没成桶。
- 以记录完整率、绑定率、桶覆盖率作为记忆质量或换窗放行标准。

保留的可靠性要求：已经发起的写入不能假报成功；真正启动的换窗提醒需要明确完成凭证；错误/超时不能冒充主模型主动选择不记。

本文中的逻辑模块名、字段、工具和接口均是实施目标，不能当成已存在代码。GLM 先读现有代码并建立真实映射；优先复用，不另建一套聊天平台、记忆库或常驻小模型。

效力顺序：用户最新明确决定 > 本文在本任务内的要求 > 未被替代的 Mariposa/estómago 当前合同 > 历史文件和参考项目。本文不改召回入口矩阵、Jev、COUNT 预算、心情/回忆访问、删除申请、关系纠错及无遗忘规则。

## 1. 产品语义：选择记忆，不做聊天全量归档式写桶

### 1.1 两条不同的保存线

**原文线**：获授权房间的真实用户消息和正式发布的模型回复，先本地持久保存，再按既有 outbox 同步 Mariposa 原文域。未 hold、未绑定、静默、跨日、缓存过期或退出模型输入均不能导致自动删除。

**记忆线**：批准身份下的主模型调用既有 Mariposa hold。桶可以有选择地记录经历；模型可以不为某件事建桶，不用逐项写“不记原因”，不需要额外模型复审它的选择。

持久原文不等于无限上下文。退出工作集的原文仍保存；是否能被 Mariposa 搜到取决于同步、授权、索引和既有原文门禁，不能宣称仅存本地就已可全库召回。

### 1.2 用户示例的规定行为

```text
m1–m4  起床、上班、早餐
m5–m8  上班发生了 XX 事
        主模型成功 hold 了 XX 事
        宿主记下当次请求的可见消息书签（示例 m8）
m9–m15 后续聊天
        即将换窗
```

默认只提醒主模型考虑 m9–m15。早餐没有 hold，不因此强制重新检查或补桶。模型主动想起更早的内容并决定补记，可以按现有权限调用 hold，但系统不强制要求全窗扫漏。

若本窗没有一次成功 hold，也没有已经完成的同范围提醒，则提醒范围为当前窗口实际携带的原始对话。即使最终零条 hold，也可以正常换窗。

### 1.3 不混用三个节点

- **hold 书签**：后续提醒从哪里开始关注。一次成功 hold 不代表此前每件事都已入库，也不证明此前原文已逐条审阅。
- **提醒完成凭证**：主模型针对某次固定提醒范围作了决定；零新增 hold 也能完成。
- **窗口边界**：控制输入规模和重建启动资料。hold 不触发立即换窗，窗口也不要求必须产出 hold。

书签不控制删除、可见性、索引、原文授权或检索范围，不叫 summarized_until、forgotten_until 或 fully_held_until。

## 2. 职责：不需要小模型

### estómago 宿主

使用普通代码检查输入容量、闲置间隔、回合状态、成功 hold 收据和当前提醒凭证。决定何时提出换窗、何时递话、何时执行切换。这个检测器不做语义判断，不调用 LLM。

### 当前主模型

继续负责现场理解、主观记忆选择及正式 hold。收到提醒后，可不写、写一条或写多条；不要求把提醒范围概括成摘要，也不要求证明每条原文都被某桶覆盖。

### Mariposa

仍是唯一正式记忆和原文证据域。验证现有 hold 字段、来源、主体、版本、幂等和状态。不会因为宿主发出“准备换窗”而自行批量写桶。

语义事件生命周期可服务于已经明确需要持续跟踪的事件、plan 和工具任务；不为每段闲聊强制分配 OPEN/QUIESCENT/CLOSED。确有未完事项沿既有领域状态和原文引用承接，不另造未完故事摘要。

## 3. 最小状态与书签算法

以下名称仅作逻辑示意，允许复用现有运行表和字段：

| 元数据 | 用途 |
|---|---|
| `context_epoch_id` | 后台上下文窗口，不改变前台 room |
| `dialogue_manifest` | 本窗实际携带的真实消息 ID、顺序、修订和来源；区别于额外定点读取的资料 |
| `last_hold_bookmark` | 本窗当前运行中最近一次已正式成功 hold 所对应的输入可见高水位 |
| `last_review_receipt` | 已完成提醒的 ID、确切范围/版本、结果；不是新的语义记忆 |
| `rotation_request` | 换窗原因、冻结的旧窗版本/高水位、提醒状态 |

### 3.1 书签什么时候推进

仅在本次主模型实际发起的 hold 获得 Mariposa 正式成功收据之后推进。记录的是**模型生成该调用时实际看到的聊天输入高水位**，不是：

- hold 中引用事件的发生日期；
- 桶绑定原文中最大的 source ID；
- 收据晚到时房间恰好已经新增到的最新消息；
- 某个后台导入、另一房间或外部客户端新写了一条桶的时间。

调用意图、模型说“已经记住”、HTTP 模糊成功或未核实的跨服务结果都不能推进。重试返回同一收据不产生新书签。迟到结果只关联原请求/原窗口，不能覆盖新窗口的书签。

此推进只表示“以后默认从这次记忆动作之后开始提醒”，不表示宿主已经验证模型考虑了此前所有事情。

### 3.2 提醒范围怎么定

在安全回合边界冻结当前模型**已见**的真实对话高水位 T 和来源修订。起点优先取本窗最近一次有效 hold 书签之后；还需扣除已成功完成的同范围提醒，避免重试切换时再次提醒。

没有 hold 书签时，从本窗实际保留的原话起点开始。上一窗传下来的有效提醒凭证可以用于避免对原样携带的旧尾段重复提醒，但不能把未曾携带/未曾覆盖的消息算作已检查。

范围按 manifest 的真实消息集合及其修订界定；跨窗携带、多个来源或不连续资料不能靠单一数值区间假装全覆盖。系统时间、工具返回、思考资料、内部提醒不是待 hold 的双方原话。

如果范围为空，不发收费提醒，直接进行剩余切换检查。新到但尚未送给主模型的消息先保存排队，不能塞进“已看过并检查完”的范围。

### 3.3 零新增也是完成

没有新 hold 的有效提醒凭证用于完成本次换窗流程，而不是永久禁止以后记起这些原文。页面显示“本次选择不新增 hold”，不能显示“已全部记住”或“全部原文已处理”。

旧窗口已准备好切换，但新窗口身份读取短暂失败，恢复时可复用同范围有效凭证；不要重复让模型作同样选择。

## 4. 自动换窗仍然存在：容量与长间隔两条主线

下列是前序方案延续和本次明确的工程初值，不是已部署状态或供应商固定限制。

| 条件 | 行为 |
|---|---|
| 普通连续聊天 | 同一后台窗口追加；不每轮提醒记忆 |
| 午夜仍在聊天 | 前台按日显示，后台不单独因为零点换窗 |
| 估计输入接近 56,000 token | 前台预警/宿主进入准备状态；不因此单独多叫一次模型 |
| 当前/下一完整回合预计输入接近 64,000 token 软线 | 在安全回合边界发一次换窗提醒并切换 |
| 距最后真实用户消息至少 6 小时 | 下一次真实交互时走长间隔换窗；不在六小时到点自动唤醒模型 |
| 必须生效的身份、权限、工具版本或 API/SDK 模式变化 | 按有效性和安全规则换窗；撤权不得为缓存延迟生效 |
| 一小时缓存过期 | 只影响缓存复用，不单独触发 hold、语义闭合或换窗 |

**64k 是当前一次完整输入的容量软线，不是累计计费 token。**每轮请求反复读取的历史不能累计到窗口占用中；但当前请求里的 cache-read token 必须计入窗口容量。

56k 是界面预警起点，64k 是准备换窗的软线；它们都不是“自动压缩到来的固定时刻”。本方案不启用滚动摘要或供应商 compaction。

### 4.1 为提醒和 MCP 预留空间

不能用完窗口后才说“请再写几条 hold”。请求前需要预算：

```text
本次最终完整输入
+ 配置允许的本次输出
+ 必要工具往返输入预留
+ 换窗提醒与 hold 的处理预留
+ 安全余量
<= 所选模型/端点实际可用上下文容量
```

提醒/hold 处理预留初值 8k、安全余量初值 4k；工具返回按现有逐请求限制预算，不能把多个 8k 当成无限总预算。最大输出和推理模式沿用当前授权配置，不能为了缓存或容量偷偷调档。

实际模型较小、输出预算较大、输入含大媒体或 SDK 有更低自动处理门槛时，软线必须提前；强制启动资料本身超预算则报告具体缺口，不静默删 I。具体有效阈值由宿主计算，界面显示实际值及原因。

56k/64k 都是预警与调度线，不是盲目硬截断：提醒请求可在实际硬容量和保留预算内高于软线。硬容量检查必须对包括提醒在内的每一个请求成立。

### 4.2 一个大输入突然到来

原窗口只有 45k、但新消息/附件会令下一次输入超过软线时，先保存新消息。用旧窗已见对话作必要提醒，再让新消息在新窗出现一次。它不能提前被计入旧窗提醒完成范围。

附件与大工具结果应在首次输入前按来源范围读取或分页。不得先塞入全部原文、下一轮再改成摘要以掩盖超限。

## 5. 提醒只递给主模型一次，不另读一遍尾段

### 5.1 请求形式

沿用旧窗的规范化完整输入轨迹，在末尾追加一条短的宿主控制事件。不要从数据库再取 mN～mT 全文重复粘贴，因为这些原话本来就在该次输入里。

提醒通过当前 OR 型号与协议验证支持的承载格式发送。**业务上由宿主发出，不等于随意添加 `role: system` 就会被 OR 放在历史末尾。**适配器可能合并 system 到前面，破坏缓存；必须核对最终有效布局。

第一版可在开窗的固定系统规则中一次性声明控制事件格式，动态事件使用明确的 runtime 来源标识及宿主内在元数据追加。即使供应商兼容格式使用 synthetic user，也不得把它保存为宿主用户实际说的话。用户伪造相同文字不应获得控制权限。

不把维护秘密、模型私有推理或有权限的资料写入提示例子。控制事件只含必要范围/标识和指令。

### 5.2 建议提醒模板

```text
[宿主控制事件：换窗前记忆检查]
原因：上下文容量软线 / 长间隔恢复 / 已批准的版本切换。
提醒范围：本窗最近一次成功 hold 书签之后，至本次冻结高水位。
这些原话已在当前输入中，无需重新获取或复制。

请自行判断这段内容中还有没有你想写入 Mariposa 的事情。
可以零条、一条或多条；不要为了覆盖聊天而强行建桶。
已经 hold 的不重复写，更早未 hold 的内容不要求回头补齐。
不要生成会话摘要，不用把所有话题判定为结束。
有要记的就调用既有 hold；没有就明确完成本次检查，允许换窗。
本事件不是宿主用户的发言，不对聊天界面生成额外回复。
```

范围与高水位由宿主填入机器标识；不要每轮重写最前面的系统提示词。

### 5.3 主模型的完成权

优先复用现有宿主完成回执。若缺失，增加一个**始终在工具清单内的宿主控制工具**，逻辑名可为 `context_review_complete`：

```json
{
  "review_id": "host-issued-id",
  "decision": "no_new_hold"
}
```

另一合法值是 `holds_completed`。具体写入列表由宿主从成功收据核验，不接受模型随口填写几个桶 ID 就算成功。无需为 no_new_hold 强制写长理由、摘要或重要性评分。

本工具不是 Mariposa 写桶工具，不创建正式记忆；只对当前房间、当前版本、当前活动 review 有效。正常聊天时无活动 review 的调用不能偷偷触发换窗。提前把 schema 固定到本窗工具清单，不在提醒时临时换整套 tools、强制改 tool_choice 或切换输出格式。

模型选择 `no_new_hold`，并且没有已承诺但未解决的写操作时，宿主允许切换；不找小模型复审。写完若干 hold 后提交完成凭证，也允许切换。

完成凭证的语义是“本次可以换窗”，不是“世界上所有事情已经完成”。独立的 plan 和真实未完工具任务仍按既有规则保存。

### 5.4 没有结果不是主动不记

网络失败、输出被截断、工具出错或没有有效完成回执，记录为本次提醒失败，不自动变为 no_new_hold。最多进行有界恢复/重试，不能无限重复提醒。

已成功 hold 的副作用不重做；新请求沿既有幂等操作恢复。模型最终决定不再写某项时必须使用现有取消/错误处理规则，不能把不确定写入结果当成未执行。

此要求只针对已经启动的提醒或实际发起的写入；不再把普通聊天里所有“没调用 hold”的内容视为失败。

## 6. 探针位置：两次检查、一次回填，不是小模型

在 estómago 的共享宿主与 OR 请求适配层实现；不放进 Mariposa 搜索器，也不做独立巡查服务。

```text
用户消息 / MCP 返回 / 运行事件到达
    ↓
先保存与验证（消息和工具结果分域）
    ↓
生成候选输入的只读投影
    ↓
P1：容量与换窗预检
    ├─ 正常：本轮照常处理
    └─ 需要换窗：排队新内容，冻结已见高水位，追加一次宿主提醒
    ↓
供应商适配与缓存断点规划
    ↓
P2：最终发送前校验（已含提醒/工具/schema/媒体）
    ↓
调用 OR
    ↓
模型输出 / MCP 工具循环（每次续请求重复 P1/P2）
    ↓
P3：接收真实 usage、工具收据、完成凭证与结束状态
    ↓
更新运行记录和前台；安全边界才切窗口
```

### P1：在系统递话前

检查已见范围、最新持久化回合状态、当前完整输入预计长度、下一步增长预算、是否已有提醒、是否达到闲置条件。决定是否需要递话，不判断内容值不值得记。

刚收到 MCP 结果时也运行，因为一个工具返回就可能明显拉长输入。若工具链尚未安全结束，只登记换窗意图并控制后续增长；不得把孤立 tool_result 搬到新窗或在工具事务中途切断。

### P2：在系统递话后、网络发送前

重新校验**实际要发送的完整请求**：token 预算、旧前缀是否保持、tools 顺序/schema、缓存标记/TTL、来源角色、模型/路由、附件、思考协议等。

P1 不能取代 P2：提醒自己也占输入空间，供应商序列化也可能改角色和块结构。至少在自有适配器边界能证明最终发送 payload；OR 内部不可见变换如实标未知，不声称看到了上游全部内部输入。

### P3：响应后的实际证据

读取 OR response 的 `prompt_tokens`、`completion_tokens`、`prompt_tokens_details.cached_tokens`、`cache_write_tokens` 和可得 `cost`，按 request_id 和用途记录。

OR 的 `prompt_tokens` 口径已经是总 prompt 数，cache 详情是其中分类，不能再相加一次。原生 Anthropic/某些 SDK 的非缓存 input 与 cache 字段需按其契约另行归一，不能混用两种公式。

流式最终 usage 缺失写 unknown，不能用零掩盖。下次输入占用以当次真正要保留的轨迹计算，不能把所有历史请求的 input 或所有含隐藏思考的输出简单累计。

### 6.1 计数器与缓存探测的区别

默认用已校准的本地计数/估计适配器，加响应真实 usage 校准。模型、tools 结构、媒体和配置变化后重新校准；标明 estimate 与 actual，不能用固定字符比例假装精准计数。

本轮没有验证 OR 当前兼容路径具有与官方 `count_tokens` 等价的可用预检端点，不能要求用户为计数改用官方 key，也不能新增未经授权的全文外发路径。

Anthropic 的 count_tokens 是估计接口，并不运行缓存读取/写入；一次计数不是保温、更不是命中证明。缓存是否实际命中看 P3。不要在每次真实请求前另发一次付费模型请求“测一下热不热”。

## 7. 缓存结构：不推倒，只把提醒接到尾部

继续使用 OR Chat Completions 并列适配器，保留 SDK 与 MCP；不暗中替换用户选择的模型、上游或模式。

请求控制片段（不是完整请求体）：

```json
{
  "session_id": "stable-opaque-room-and-model-profile-key",
  "provider": {
    "only": ["anthropic"],
    "allow_fallbacks": false,
    "require_parameters": true
  },
  "cache_control": {"type": "ephemeral", "ttl": "1h"}
}
```

`anthropic` 指 OR 中的供应商选择，不是改为官方直连。上线时核对所选精确模型的 endpoint slug 和能力，不默默降 5m。不要用不同 session_id 为聊天、提醒和同窗工具续请求人为分流。稳定 ID 仍不能保证所有上游缓存都命中。

保持原布局：

```text
固定 tools + 批准运行规则 + 本窗口 I     → 固定点 A
本窗口 Mariposa 启动资料快照           → 固定点 B
近期原话 + 不可变历史 + 新增输入/提醒/工具往返 → 自动前移点
```

全部使用 1h；供应商允许的断点总数、最低长度与回溯范围由适配器验证。自动尾点占一个名额，不能给每条历史永久累积标记。

### 7.1 三个禁止改法

1. 不在旧历史中插入“这里 hold 了”的文字；书签存元数据，前台以装饰标识显示。
2. 不为了提醒每次改最前面的 system、重排 tools、删掉工具、改 tool_choice/推理档位。
3. 不为“仅检查尾段”把完整旧前缀改成单独截取的尾段请求，除非这是记录清楚的恢复路径；主路径保持旧前缀，只在指令里限定关注范围。

历史动态时间、工具结果、召回资料第一次注入后固定成当时的运行快照，下一次只新增，不能用最新值覆盖旧值。提醒自身进入运行轨迹，但不进入双方原文或 Mariposa 记忆。

正式 hold 在 Mariposa 立即生效；本窗 A/B 不因每次 hold 重建。工具结果追加后模型知道刚刚保存了什么，下一窗再读新快照。权限撤销和关键纠错优先于缓存。

### 7.2 费用解释

当前对话已在主模型上下文，不代表 API 下一次请求不必携带它。兼容 API 路径仍应重建相同历史输入，命中的前缀按缓存读计费，新增提示和工具链按实际用量计费。

主路径避免的是：再让另一个模型独立分析同一段材料，以及重复粘贴已经在输入里的原文；不是承诺检查免费或所有模型组合下主模型必定最便宜。前台单独记录 `pre_rotate_review` 的真实费用。

## 8. 不启用压缩；SDK 额外处理真实 hook 能力

### OR

本方案主动控制窗口，不开启服务端 compaction、客户端滚动摘要或静默 middle-out/context compression。按当前端点的正式字段关闭可能继承的压缩/截断配置，并核对 preset 等实际配置；不能只在界面隐藏压缩按钮。

2026-10-05 查阅的 OR 文档使用 `plugins: [{"id":"context-compression","enabled":false}]` 表达关闭；GLM 必须与实际请求版本核对，不凭旧示例认定一个空 transforms 数组涵盖所有路径。请求过大时应在自有 guard 拦下，不依赖上游删中间内容来返回 200。

### SDK

保留宿主的提前容量检查，并按已安装 SDK/Claude Code 版本核对 `PreCompact` / `PostCompact` 支持。只读官方文档不等于用户本机已支持。

当前 Claude Code 文档规定 PreCompact 可用退出码 2 或 `decision: block` 阻止压缩；但若是在超上下文错误后触发的补救压缩，阻止它仍会使原请求失败。文档还规定其 `systemMessage` / `continue` 不作普通递话处理。

因此：PreCompact 是兜底控制/告警入口，不是唯一容量探针，也不是等到最后一刻给主模型塞 hold 提醒的可靠通道。正常提醒在宿主安全边界提前发送。若版本不能可靠阻止自动 compact，要明确标兼容性缺口，不能偷偷让摘要进入启动包或 hold，更不能伪报通过。

不为本任务擅自升级 SDK、修改全局网络/认证、切换正在使用的模型模式或移除既有思考隔离合同。必要的模型协议签名字段与既有不回灌思考规则冲突时保留阻塞/核对，不伪造签名。

## 9. 切换顺序、长静默与新窗启动

```text
确认换窗意图；保存新来的消息
→ 完成/妥善暂停当前真实工具回合
→ 冻结旧窗已见高水位与版本
→ 计算最近 hold 书签之后的提醒范围
→ 范围非空且无有效凭证：旧窗主模型完成一次检查
→ 主模型选择零写入，或所选 hold 写入成功并确认完成
→ 准备新窗身份、Mariposa 快照和近期原话
→ 新窗准备成功后切 active 指针
→ 排队新消息进入新窗一次
```

没有为每段历史创建待补齐任务的步骤。没有“必须有桶才能换”的条件。前台始终为同一个 room 和完整时间线。

长静默初值仍为 6h；只在下一次真实交互处理，不在夜里自动叫模型。需要提醒时恢复旧窗的合法原始输入轨迹，针对书签后剩余范围作同一种选择；缓存已经冷掉则如实记录成本。不要借隔夜恢复扫描所有历史或后台补造当时心情。

新窗保留：当前有效 I 与批准规则、稳定 tools、既定近三日标题及合法 mood_tags、相关未完成 plan/真实已有事件状态、既定重要桶和临近纪念、近期原话初值约 12k token。启动整体约 32k 是目标，不是强制裁掉关键材料的许可。

不自动读取 mood_text、回忆、keep 理由；启动读取不算明确打开/回温。不把全部永久 WIDE 桶全文默认灌入。没有成桶的闲聊不强制生成未完事件或摘要；需要详细前情时按既有权限与来源读取。

日历变更、缓存过期、提醒完成、窗口切换，都不能将真实 plan 自动完成或把语义事件强行 CLOSED。

## 10. 前台必须增加“记录”按钮

这是本次必做 UI，不是可选后台日志，也不替换完整聊天记录。复用现有聊天头部/模型状态入口，在桌面打开侧栏、手机打开底部面板。保持现有画风，不改 Enter 换行和独立发送键。

### 10.1 按钮与面板内容

按钮文案：`记录`。未展开时可有轻量容量状态，不占据大块聊天区域。

面板至少显示三组信息：

**上下文与换窗**：当前后台窗口、模式、精确模型、当前输入 estimate/上次请求 actual、实际有效软线、模型硬容量（已知时）、预警状态、上次换窗时间与原因。不要将 64k 画成模型的最大能力。

**hold 与提醒**：本窗真实成功 hold 的时间、桶引用、对应聊天书签；本次提醒范围、提醒是否已发送、主模型选择“未新增/新增 N 条”、错误状态以及换窗结果。不得把未 hold 计数做成红色错误或“漏记率”。

**缓存与费用**：配置 TTL 1h、上次请求读/写/非缓存输入及费用、上次真实命中证据、提醒用途花费、Keeper 开关状态。热截止只能标估计；没有 usage 时显示未知，不能显示 100% 命中。

文字演示，以下数字均为虚构 UI 样例：

```text
记录
当前窗口：12 · OpenRouter · 已配置模型
当前输入：约 58.2k / 换窗软线 64k（预计值）
状态：接近换窗；当前回合结束后检查

10:16  hold 成功 1 条        [定位原话书签] [桶引用]
11:03  换窗提醒已发送        范围 m43–m70
11:03  主模型选择不新增 hold
11:03  窗口 12 → 13          原因：容量软线

缓存配置：1h
上次请求：读取 54k，写入 3k，非缓存 1k（示例）
保温：未启用
```

### 10.2 书签显示与点击

书签是成功收据驱动的前台装饰，不修改原消息正文。定位按钮只滚动到原话位置，不能追加一条模型可见“已记忆”消息破坏前缀。

“查看桶”按 Mariposa 原有明确打开/权限语义执行；仅看运行记录不能暗中执行 open→confirm 或改变召回阶段。

默认展示标题/ID/状态等获授权元数据；不在日志面板复制完整私密 prompt、模型推理、秘密或后台全部原文。用户在同房间获授权的原文查看仍走原有界面。

### 10.3 只读入口

打开、关闭、刷新记录面板，以及页面重连，均不得发起模型调用、hold、提醒、保温或换窗；不会重置真实用户活跃时钟。

后端优先复用现有事件订阅/SSE 和运行状态查询；若需新接口，提供 room-scoped 只读快照和有界分页事件，名称由 WP0 映射。不为此新增第二套事件事实库或复制聊天全文。

UI 能清楚区分：`本地已保存`、`原文待同步/已同步`、`hold 成功`、`提醒完成但零新增`、`切换完成`，不能用一个模糊“已记住”覆盖这些状态。

## 11. 异常、并发与无副作用边界

- 每房间已有模型执行、工具结果交付、换窗提醒和切换使用同一串行/版本约束，别开多个并发模型互相抢指针。
- 同一提醒绑定固定 review_id、epoch、范围和修订；去重重试不会重新产生桶、继续移动书签或形成多条成功记录。
- 提醒中来了新用户消息，先保存排队；旧凭证不能覆盖未见新消息，换窗后新消息只注入一次。
- 主模型选择零新增是成功；API 错误/空结果/输出截断是失败。界面不把两者混为一谈。
- 已尝试 hold 的网络结果不明确，按既有操作回执核实，不在不知结果时再次随机生成一次写入。
- 身份读取失败不能生成默认空身份助手，也不能先销毁旧窗；切换失败可复用有效提醒凭证。
- 逼近硬容量又无法取得有效提醒结果时，保存新消息并显示待恢复，不能盲发超限或静默删前文。修复只针对本次任务，不恢复全库自动补记。
- 用户编辑/删除/撤权后按有效版本处理；旧范围凭证不能跨无效修订偷用。保留原有依法/依授权删除与纠错机制，原文全存不等于撤权失效。
- 不递归触发：`pre_rotate_review` 结束不得再触发新的同范围 review。
- Keeper 暂不运行；以后可共用调度器，但 `cache_keepalive`、`pre_rotate_review`、`proactive_turn` 是独立用途。保温不能写 hold 或发聊天；提醒不冒充免费保温。

### WP0：只读映射

### WP1：收回过度的全量补齐

### WP2：书签、一次提醒和安全切换

### WP3：容量探针与 OR 缓存

### WP4：前台“记录”按钮

必做桌面侧栏与手机面板、容量估计/实际标识、hold 书签定位、提醒决定、换窗事件、读写缓存和费用。打开面板无模型/记忆副作用。

### WP5：交付与验证

交付实现 commit、接口差异、逐项测试证据、脱敏 payload 结构、usage 证据或明确未执行状态。真实 OR smoke 需在既有明确小额授权内；未授权不调用付费模型。生产部署另按既有授权，不偷换正在运行实例。
