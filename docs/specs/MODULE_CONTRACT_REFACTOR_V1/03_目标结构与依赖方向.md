# 目标结构：少量明确接口，不造插件平台

## 一张文字结构图

```text
HTTP / 模型工具 / 到期调度 / 用户消息
           ↓（各自可信入口；不是互相伪装）
   application/ 对应的用例与组合流程
           ↓
   稳定能力执行接口 + 领域公共服务
           ↓
modules/<域>/（定义、执行、投影、政策、接入仓库）
           ↓
integrations/<服务>/adapter（现有HTTP/流协议）
           ↓
  Mariposa / Siren / oído / 许愿星

runtime 主循环：只认识回合、冻结目录、执行器、上下文贡献与取消
messages 正本：只发布有类型生命周期事实；不认识“浮现模块”名称
app-context：显式创建和注册，不编写具体业务流程
```

不是所有东西都必须走 registry：本地 MessageService/WindowManager 等宿主基本服务保持真实调用；registry 管能力暴露与调用政策，不成为全项目的服务定位器。

## 固定的目标目录（允许在已有等价文件内落地，必须在映射表说明）

```text
apps/host/src/
  capabilities/
    contracts.ts            # 叶类型；不导入具体模块
    registry.ts             # 显式登记/查找/重复名检查；无业务分支
    executor.ts             # 通用校验/准入/生命周期/执行/结果边界
    model-bridge.ts         # catalog/define/invoke、冻结定义/已见校验
    validation.ts           # 从既有validateToolArgs提取的通用形状校验
  modules/
    oido/                   # 深听能力与源绑定；现有adapter继续复用
    voice/                  # call_control、transcript_read、通话入口与组合
    memory/                 # Mariposa工具、词表、来源核证、模型投影
    conversation/           # conversation_read、正式发布、附件发布
    wake/                   # wake_manage、background_complete、后台用例适配
    content/                # 发帖、评论、作品
    wishstar/               # 许愿星现行工具组
    identity/               # identity_milestone_write（非Mariposa I）
    media/                  # media_import、media_search；复用资产/index服务
    context-review/         # context_review_complete既有本地规则
  application/
    module-composition.ts   # 唯一静态装配清单（名称可与现有 composition 根合并）
    voice-hearing.ts        # 语音素材/转写/深听的明确组合；不处理全项目
    background-execution.ts# 调度任务→同一supervisor回合入口
    message-lifecycle.ts   # 已发布/编辑/提交后挂点的装配，保留事务
    context-contributors.ts# 开窗资料与同轮补充的固定接线
    program-facts.ts        # 需要时提取既有程序事实接受逻辑；不创建第二队列
  messages/lifecycle.ts     # 同步inTx事实与afterCommit契约
  context/contributions.ts  # 两种上下文贡献契约；不含具体记忆业务
  server/routes/            # 按域的HTTP处理器；沿用外层认证与响应格式
```

不要求每个域都拆成 catalog/service/handler/repository/projector 五个空文件。小域可 `module.ts` 一文件；memory/oido 复杂域按实际职责拆。已有 `memory-surfacing`、`media`、`context` 目录不为美观批量改名。可通过模块工厂包装已验证服务，不搬迁所有代码。

## 允许的依赖

1. `capabilities/contracts.ts` 只能依赖叶类型或内建类型；不能从 host-tools 导入上下文类型。
2. registry/executor 不导入 modules、具体 adapter、Host、Supervisor、HTTP；通过受限依赖传入。
3. model-bridge 读取冻结工具与定义可见性；不拥有业务处理器。host-tools 在最终可删或只做明确兼容重导出。
4. modules 可依赖 contracts、自己的内部实现、既有外部 adapter、已注入的窄宿主服务。
5. modules/A 不导入 modules/B 的内部文件。跨域流程 application/ 同时拿 A/B 的公共端口。
6. application 可导入具体模块工厂做装配；单个业务组合只依赖所需端口，不拿所有模块集合随意 lookup。
7. runtime/supervisor 可依赖 registry的只读快照/执行接口、context/lifecycle接口、现有运行服务；不能再 import OidoAdapter/MariposaClient 或按 `oido_*` 名称判断业务。
8. server总入口处理认证、解码、分派、共同错误映射；域handler调用同一领域方法，不能复制模型工具那套业务规则。
9. 共享SQLite可以保留。物理连接共享不代表逻辑所有权消失；仓库内部访问本域/宿主接入映射表，跨域通过公共读取/发布方法。

## 正常扩展时允许改什么

新增现有工具型能力：对应模块实现/定义/投影/政策/测试，必要时模块注册条目和前端入口。
新增生命周期消费者：消费者文件 + 装配声明；不修改消息接受/编辑/发布事务的主算法。
新增上下文消费者：贡献者文件 + 装配声明；不得逐业务修改prefix/轨迹算法。
新增普通预约用途：参数/用例声明；不改调度器核心或复制模型循环。

配置schema汇总、显式构造参数、路由注册、UI挂点的合理变化不算失败；但必须是声明或薄适配，而不是把业务逻辑重新塞进中心文件。

## 模块声明必须真正有效

声明的工具要被实际模型bridge/HTTP用例调用；声明的生命周期处理要进入真实Host.start/stop；声明的context贡献要经过真正发包。不要写一份 manifest 之后旧代码继续照常硬接。

本专项完成时必须有：工具所有权表、公共接口清单、生产调用路径证据、旧入口删除清单、常见故障影响表。不能只交目录树。
