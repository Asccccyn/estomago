# 给 Astra：架构独立演进与最终收口复核

先独立读取同一候选SHA与diff，再看Flash/GLM5.3报告，避免用别人结论替代判断。遵守共同规则与07测试限制。

## 核心问题

- registry是否真实运行，还是巨型旧executor外面套壳？同名能力是否唯一owner？
- 定义、handler、费用、投影是否一起归属模块？增加普通能力是否仍需改多个核心名单？
- 依赖方向是否合理：叶类型不反向依赖业务；modules不读兄弟内部；application组合不变新上帝类？
- 源/发布/权限的正本是否清晰；模块只拿窄端口而非整个Host/Db万能对象？
- 生命周期是同步事务登记+提交后唤醒，还是丢失可靠性换成内存广播？
- 缓存/window工具与上下文贡献边界是否完整；保留全部finalAdmit/cancel/frozen语义？
- 自主/保温与普通聊天是否仍同一真实执行位；内部步骤授权/费用/取消有没有绕过或重复？
- voiceTap/音频流是否避免进入通用事件系统；前端重连有无重复订阅/重复派发？
- 所有旧分支/兼容fallback/timer是否退役，缺失模块是否只影响相应能力？

## 必要独立证据

阅读CHANGE_LOCALITY的实际diff，不只看描述；复查扩展探针确实无需改核心。重跑结构guard并人工核对其漏检范围。选一个普通组合、一个常见取消、一个旧窗请求对照即可验证关键接口，不另写极端套件。

如果建议拆更长函数，必须说明当前独立演进问题，不以行数定罪。若需要外部合同变更、真实收费或新业务，列为独立后续，不强迫Flash在本专项“顺便做完”。
