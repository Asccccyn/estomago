# P10 · 冻结交付与双人复核


## 目标
交可复核、可集成、未越权部署的候选。

## 步骤
1. 按08生成完整报告，真实填验收状态。脚本validate_delivery可查格式但不代签PASS。
2. git status确认自己的未提交范围；按明确文件stage，不用git add -A/.，提交描述自己实际修改。
3. 记录候选SHA与来源SHA；重新查看来源是否推进，说明接缝冲突。不要为赶交付自动重写历史。
4. 如前端改动，单次构建自己的产物；区分源树已有dist改动，不能宣称已整合它们。
5. 给GLM5.3 `review/01_GLM53复核.md`；给Astra `review/02_Astra复核.md`。两者对同一候选独立阅读；实施者自测不是其中一份。
6. 复核发现按证据分级处理，只修本专项真实问题；无产品路径的极端猜想转建议，不扩散施工。
7. 交付 `GLM_DELIVERY.md`，明确：源码/离线合同/隔离HTTP/真实收费/生产分别什么状态。
8. 默认停在发布候选，不合回生产、不重启、不开启flag。未来上线须按09另行批准。

## 最终答复模板
“专项候选 `<sha>` 已完成/部分完成。真实迁移的模块为…；旧接线退役…；定向测试…；未执行…；阻塞…；生产未改动。复核入口…。”
不得答“所有功能已可用”“已经稳定不再耦合”“100%无bug”。


## 本卡统一退出记录

写明：起始SHA → 本卡提交；实际改动符号；与原行为对照；定向测试命令/退出码；未做部分；下一卡。
本卡PASS不自动使整个专项PASS。模型不可为“让本卡通过”改变01的裁定。
