# P02 · 注册表接入第一条真实能力


## 目标
让oido_get成为第一个真正经过模块注册/执行的新路径。只建registry而没有Host调用即FAIL。

## 先读
03、04、05；host-tools.oidoGet/oidoAnalysisAllowed/oidoSourceAllowed、integrations/oido/model-view.ts；app-context工具装配；既有oído源绑定表相关代码。

## 子步骤
P02.1 实现最小registry：显式注册、重复名拒绝、按既有baselineOrder枚举、resolve只返回声明能力。注册时检查同名/handler/投影/政策存在，不访问远端、不动态授予新能力。

P02.2 实现通用executor外壳，但从现有execute的真实顺序提取，不重新发明错误语义。先保留event payload、参数校验、beforeBackgroundTool、seenAdditions/imageRefs与取消方式。

P02.3 为oído接入提取窄source repository：当前会话asset可读、analysis↔源绑定、交付前重检。保留当前SQL条件与已发布限制；不为测试把门放宽。仓库只管理这些est接入表，不管理整个聊天库。

P02.4 将oidoGet实际实现移到modules/oido/service.ts的公共用例。使用原OidoAdapter、原model-view。拆内部结果与模型投影时确保oidoModelView只执行一次，参数/detail/cursor/失败码完全一致。

P02.5 在modules/oido/module.ts登记oido_get定义、handler、既有费用报价政策与显式模型投影。默认其他工具尚未迁，不顺手迁整个项目。

P02.6 真正接入Host创建的工具执行器。临时迁移路由是“名称属于已迁集合→新executor；名称属于尚未迁的明确集合→原handler”。集合必须不相交。**绝不在新路径失败时回退旧handler。** 定义也只存在一个来源，原oido_get定义删除/委托只读同源，不双注册。

P02.7 从真实Host入口经tool_define/invoke调用oido_get。必须先通过正常发布/分析建源绑定；fake外部响应可用。记录进入新handler计数=1、旧handler=0，响应/错误/取消与基线相同。

## 费用注意
oido_get在当前verified-free名单之外。不能凭“get”名称改为免费；沿用当前可信报价配置/BUDGET_ESTIMATE_UNAVAILABLE规则。投影也不能默认返所有raw字段。

## 完成标准
真实Host→model bridge→registry→新handler→边界fake HTTP→模型投影闭环；旧oido_get业务已删。仍未迁的工具在MIGRATION_MATRIX明确列出，整个专项不得因此宣称完成。
