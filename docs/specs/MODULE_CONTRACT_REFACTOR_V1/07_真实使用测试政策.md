# 测试政策：从真实使用出发，不再用极端夹具主导产品

适用于实施者、GLM5.3、Astra以及另行邀请的Codex。此文件是本专项验收边界，不是“可选建议”。

## 1. 每个业务测试先写四句话

场景：宿主用户/char在界面或工具上做了什么？
前置：该状态怎样由正常接口到达？
风险：失败会造成什么真实问题？
断言：用户看到什么，系统实际发了几次请求/写了几条/是否收费/是否进入当前回合？

写不出前三句的业务测试，不新增。不得用“理论上可能”直接升级为阻断验收项。纯参数解析/投影函数的普通单测可以直接给输入，但不能把其结果冒充发布/授权业务验收。

## 2. 本次允许且必须有的三类

**NORMAL**：文字聊天、发语音、已发布语音深听、记忆读取/写入、预约后唤醒、工具组合、同轮浮现、按天/前端相关入口照常工作。
**COMMON_INTERRUPTION**：点一次停止、编辑一次后发送/重试、手机断网后重连、请求超时一次、关闭某个模块/开关、正常重启后恢复。保留已有真实回执与生命周期。
**ESSENTIAL_BOUNDARY**：未发布草稿不能被模型读取、他房间资产不可读、未知写结果不重放、工具调用不重复收费、历史不改写、迟到结果不覆盖新修订。这些不是“极端情况”，保留有限代表场景。

## 3. 本次明确不跑、不新增

- 人工造出从未发布、没有合法源绑定的transcript，再要求模型成功读取。
- 手改DB塞出产品不会产生的任意revision/status组合，随后要求业务支持它。
- 一百万消息、百并发调用、无限递归工具、随机故障组合、深层代理套娃、穷举所有开关组合。
- 文件系统全盘损坏、SQLite随机位翻转、未支持的多机部署、未来情绪系统完整E2E。
- 无真实语义变化却不停换几种数字/排列增加计数的重复测试。
- 为测试方便突破权限、跳过已发布门、将读失败包装为ok=true。
- 为追求全绿恢复已退役旧合同、全局skip现存失败、重录golden掩盖变化。

## 4. 旧测试先分类，不盲跑全仓

`templates/TEST_INVENTORY.json`记录每个候选文件及必要的测试名，类别为上面三类或 HISTORICAL_CONFLICT / UNREACHABLE_FIXTURE / OUT_OF_SCOPE。

候选文件名在 `contracts/curated-test-candidates.json`，只是导航，初始均NEEDS_CLASSIFICATION。名称含audit不意味着可跑，名称含unit也不意味着纯函数。

混合文件：保留正常/必要场景到专项定向文件；旧错误/重复场景按实际裁定删除或修正，写“旧预期→现行语义→可达前置”证据。已确认不可达的历史测试不作为本次执行门；若尚无法确认，不先改代码迎合它，也不称它通过。复核者检查分类是否借机删保护。

本次不自动执行无选择器的 `npm test`。运行选定文件使用既有runner：

```sh
/opt/homebrew/bin/node scripts/run-tests.mjs \
  --file=tests/unit/tool-discovery.test.ts \
  --file=tests/unit/tool-initial-visible.test.ts
```

上例也须先完成分类。runner会处理临时home和凭据保险丝；不要手动指向生产ESTOMAGO_HOME。若保险丝拒绝，先报告具体变量名/路径风险，不打印密钥，不改保险丝；使用干净测试进程，不能修改用户持久环境。

## 5. 新增测试数量不是目标

新增业务场景以 `contracts/acceptance.json`中有限场景为正本。一个集成用例可以覆盖多个验收ID，不要求每ID再建一套数据。优先补真正缺的路径，其余引用现有有效测试。

模块权限/预算/停止依赖只能用真实代码 + 边界fake transport/runner；禁止mock整个registry/handler后断言“组合通过”。fixture必须通过正常服务/HTTP命令建立前置。系统内部特殊已有迁移态，只能由真实迁移/恢复入口生成；本次不额外扩展异常状态空间。

## 6. 正确区分四种结果

- 纯函数单测：只证明局部算法。
- Host离线合同：真实Host/DB/模块/执行器，替换外部transport/模型runner，证明本地链。
- 隔离本机HTTP联调：临时home+本机fixture服务，证明真实HTTP序列化和启停；不是生产远端能力验证。
- 真实收费/生产：本专项默认NOT_EXECUTED，需要另行授权。

“不调用真实模型”不等于只能检查静态类型；本地实际处理器、队列、数据库、HTTP和SSE可以真实跑。

## 7. 常见坏例子与替代

坏：INSERT一条ready转写，无published message，调用transcript_read断言ok。
好：通过上传/转写/发送建立已发布源，再调用读取断言正文分页正确；另一个用例停在发送前，断言拒读。这不是两种矛盾合同。

坏：让组合能力任意递归100层，要求通用框架处理。
好：已发布语音→ingest→analyze这条现有组合，第二步超时一次，确认不会重做已成功的副作用且unknown如实保留。

坏：同时触发100条心跳/唤醒/编辑，要求全状态穷举。
好：一次到期唤醒在排队时用户点击停止/到来一条真实用户消息，观察现行规则；保留一个能重复稳定复现的路径。

坏：为漂亮覆盖率把“已调用mock函数”当上线证明。
好：从Host入口记录执行到正确handler、fake transport收到正确参数、响应经模型投影返回、旧分支无调用，明确标OFFLINE_CONTRACT。

## 8. Codex专项限制

Codex不得以“审计更严格”为由擅自扩充极端测试空间。任何新增阻断项必须包含正常产品入口、可重复操作、真实影响、最小复现。没有路径的猜想标“范围外建议”，不驱动本轮补丁。

发现真实安全问题仍要记录；禁止用本政策忽略凭据泄漏、跨房读取、重复收费、未发送内容可读。只需最小代表用例，不用压力测试把问题放大。
