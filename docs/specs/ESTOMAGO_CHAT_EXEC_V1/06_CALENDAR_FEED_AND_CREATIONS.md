# 06｜日历、私密朋友圈、相册与纪念作品

## 0. 文件效力与实施目标

本文件面向 GLM，规定 est 的可选内容功能如何以最小规模接入同一个前端。est 继续作为聊天后端：负责聊天、身份认证、模型调用、基础媒体资产和轻量调度；不把阅读、星星、记忆库、社会平台浏览、作品展示等领域全部搬进聊天核心。

用户已确定：新的私密朋友圈与扎西德勒朋友圈完全独立；江乔生和周家明双方都能查看、发帖、评论。其他先前已确定的语义在本文件继续保持，尤其是桶按事件实际发生日期显示、纪念作品自愿创建、重要日期提醒不得自动拆星。

以下新增路由、工具名、数据表和适配 DTO 都是本轮**拟议合同**，用于指导新增代码；它们不代表 Mariposa、Superposition、Antinomy、Siren、oído 或扎西德勒已经存在同名 API。落地前必须读取当前代码，把已有入口映射到这些语义；能复用既有合同就复用，禁止凭本文件捏造一个外部既有接口。

编辑、删除本人帖子和评论，以及删除含有他人评论的帖子的处理方式，是本包的**建议默认**。它们不得在实现报告中写成用户此前逐项裁定过的历史事实。

本文件与媒体规范的分工：媒体规范负责上传、导入、持久化、资产授权、引用保护和聊天发送；本文件负责内容对象及其 `asset_id` 引用。冲突应先与总说明、认证和媒体合同对齐，不能各自实现两套规则。

## 1. 最小部署边界

| 部分 | 负责内容 | 部署与数据 |
|---|---|---|
| 同一前端 | 聊天及已启用内容页面、统一导航、日历聚合展示 | 继续沿用 est 当前前端，不另建用户账号和第二套登录 |
| est | 聊天核心、现有认证、基础资产、轻量调度、薄内容代理、日历读聚合 | 沿用现有进程及持久库 |
| 新增可选 `apps/content` | 三类相册的归档信息、私密朋友圈与评论、纪念作品及关联、未来留言正文 | 一个独立进程、一个独立 SQLite；默认 `127.0.0.1:18788`，端口可配置并在启动前检查冲突 |
| Mariposa | 桶、我们的话、正式计划及各自关系和权限 | 保留现有服务和正本，不迁移到 content |
| Superposition | 星星、重要日期、邀请和拆星状态 | 保留现有服务和正本 |
| 其他已有服务 | 阅读、语音、听觉、扎西德勒、外部浏览等各自业务 | 保留各自后端；按总说明接 MCP、HTTP 或既有适配器 |

所有服务可以部署在同一台 Mac。独立后端不等于再买一台服务器。`apps/content` 中的 albums、feed、creations、future-notes 是几个清楚的小模块，共享一个 SQLite；不再给每一项功能创建服务、调度器、消息队列或新数据库。

浏览器只调用 est 的公开面。新增内容路径统一为 `/api/v1/content/*`，由 est 验证当前会话后，薄转发到 content 进程的同名路径。content 只监听 loopback，内部请求必须验证服务凭据和由宿主派生的 actor 上下文。仅限制 loopback 不能代替内部认证。

content 进程不在同步请求中反调 est 验证媒体，也不直接连接 Mariposa 数据库。媒体、跨源对象验证和必要读取由 est 的适配器负责。避免形成 `est → content → est` 的同步等待链。

content 停用或故障时，聊天仍可使用。前端按启用状态显示入口；已经打开的内容页面明确显示服务状态，不用“暂无内容”掩盖连接错误。

## 2. 数据正本与读取规则

| 数据 | 唯一业务正本 | content 或日历允许保存/显示什么 |
|---|---|---|
| 聊天消息、按天原文 | 当前代码中的既有原文/消息存储 | 通过只读适配器查询或定位，不复制成可修改正文 |
| 桶正文、发生日期 | Mariposa | 保存稳定桶引用，读取标题、发生日期及详情入口 |
| 我们的话 | Mariposa | 截图保存关联引用；不抄一份可独立修改的话 |
| 正式计划、状态、安排日期 | Mariposa | 日历读取/通过原服务编辑；est 只保存提醒执行记录 |
| 星星、重要日期 | Superposition | 读取重要日期与安全入口，不拉取星星正文充当预览 |
| 图片、音视频、小作品文件 | est 基础资产服务 | content 仅保存 `asset_id` 和展示/业务元数据 |
| 朋友圈帖子和评论 | content | 自身正文、作者、时间、附件引用、展示样式 |
| 相册归档与作品绑定 | content | 相册类别、含义、说明、资产引用、外部稳定引用 |
| 未来留言正文 | content | 作者、正文、附件引用与版本；不拥有投递状态或自己的定时器 |
| 普通提醒、未来留言的调度和投递 | est 现有或本轮轻量调度模块 | 保存留言/计划引用、目标时间、状态和幂等投递记录；日历读聚合 |

禁止将外部桶或计划复制进 content 后允许双方分别修改。必要的标题缓存只能是可重建的展示缓存，必须能分辨过期/不可达；第一版优先请求时读取，不为这件事另建同步系统。

外部关联统一表达为稳定引用，示例：

```json
{
  "service": "mariposa",
  "kind": "bucket",
  "id": "existing-bucket-id"
}
```

`service` 和 `kind` 来自适配器允许的集合，`id` 是源服务真实对象 ID。不要把标题、显示名、URL 中可变的片段或事件日期当成对象 ID。此 DTO 是新增适配层表达，不改变外部 API 的既有字段名称。

源对象删除后，保留本地作品或截图；界面显示“关联内容不存在”。源服务暂时离线时显示“暂时无法读取关联”，两者不得混为一谈。读取关联不允许自动重建桶、补写我们的话或触发拆星。

列表、月历、搜索结果、关联校验和作品预加载都采用源服务的只读读取，不调用明确打开/续期能力（例如当前合同中的 `memory_open` / `view.confirm`）。打开一件作品或播放完动画本身也不是打开桶。只有用户或周家明明确打开桶时，才复用现有确认语义；不能在预取时提前确认，或由页面和代理各确认一次。

## 3. 身份、隐私和通用请求合同

### 3.1 actor 与授权

内部 actor 统一为 `qiaosheng`、`jiaming`，显示名分别为江乔生、周家明。它们来自现有认证和宿主执行上下文的可信映射。

- 江乔生在前端操作：est 从真实登录会话取得 actor。
- 周家明调用工具：est 从受控模型执行上下文取得 `jiaming`。
- 浏览器或模型不能靠请求体中的 `actor`、`author_id`、显示名或任意自报请求头决定作者。
- est 必须移除客户端伪造的内部身份头，再生成经内部服务凭据保护的 actor 上下文。
- content 再验证服务凭据、actor 是否在双人集合内、对象权限；不能仅信任入参中的字符串。
- 维护工具可以执行明确授权的维护任务，但不得默认冒充其中一人发帖、评论。

| 操作 | 建议默认权限 |
|---|---|
| 看帖子、看评论、看相册、看纪念作品 | 双方都可以；不开放公众读取 |
| 发帖、评论 | 双方都可以；作者由宿主派生 |
| 编辑/删除帖子与评论 | 只能操作本人内容；另行授权的管理能力不在日常工具中默认开放 |
| 相册添加、修改说明/含义、移除归档 | 作为两人的共享相册，双方均可；移除归档不等于删除所有引用的原图 |
| 纪念作品创建、添加后续作品 | 周家明可自主选择创建；江乔生也可通过同一界面提交内容 |
| 编辑/删除纪念作品记录 | 默认由创建者操作；不借此获得修改 Mariposa 桶的权限 |
| 读取未来留言 | 双方私密可见，按既有会话权限读取 |
| 创建、编辑、删除未来留言及安排投递 | 作者由宿主派生；默认仅本人管理正文和以本人身份发出的任务，用户总调度开关仍可停止后续投递 |

本空间不接关注、粉丝、公开主页、推荐流、公众评论、跨账户发现。与扎西德勒朋友圈不共用帖子表、评论表、发布任务或默认同步逻辑；不能因为名称相同就双向转发。

### 3.2 时间、分页、重放和更新

- 业务日期为 `YYYY-MM-DD`，时区为 `Asia/Shanghai`。
- 真实时间戳由服务端生成，保存为 UTC ISO 8601；展示再转换北京时间。
- `created_at` 不因编辑而变化；帖子另外保存服务端生成且不可被编辑重写的 `published_at`。第一版帖子即时发布，二者可在同次事务赋相同时间，但语义独立；未来留言的创建时间不能冒充帖子的发表时间。编辑只改变 `updated_at` 和递增的 `revision`。
- 列表 `limit` 默认 20、最大 100。超过上限返回参数错误，不返回未提示的大结果。
- 使用不透明 keyset 游标，绑定查询筛选、排序、父资源和末尾排序键。游标不能跨帖子、日期、相册类别或排序复用。
- 帖子按 `(published_at DESC, id DESC)`；评论按 `(created_at ASC, id ASC)`。时间相同仍由稳定 ID 消除歧义。资产归档/未来留言的列表可按各自 `created_at` 排序，不混用帖子发表时间。
- 首次读取记录本次遍历的上界；后续翻页保持该上界。期间新增内容通过刷新/加载新内容读取，编辑不能重排旧记录。禁止以 offset 分页应付并发插入。
- 所有产生副作用的新增 HTTP 请求，包括创建、更新和删除，统一使用 `Idempotency-Key` 请求头；作用域至少包含 actor、操作、目标资源。公开和内部代理面采用同一约定。
- 同 key、同请求返回同一结果；同 key、不同请求返回 `IDEMPOTENCY_CONFLICT`。在提交状态不明时，先用同 key 恢复结果，不换新 key 再创建一份。
- 更新采用 `PUT`，删除采用 `DELETE`，其他写操作采用 `POST`；本包不引入 `PATCH`。更新、删除统一携带 `If-Match` 请求头，与目标当前 revision 比较；不匹配返回冲突，不能悄悄覆盖。资源读取/写入返回 revision 及对应 ETag，例如 revision 为 7 时为 `ETag: "7"`，请求使用 `If-Match: "7"`。不接受通配符或多版本列表来绕开精确版本校验。
- 模型工具仍使用结构化 `expected_revision` / `idempotency_key` 参数，由 est 映射成上述 HTTP 请求头。HTTP 正文和查询参数不再接受这两个控制字段的重复版本；缺少必需If-Match返回428；缺少幂等键或头格式错误返回明确参数错误，不默认生成一套新身份或新重试键。

外部原有 API 若使用其他方法，由适配器按其已验证合同调用；上面的限定针对本包新增公开与内容服务接口。

## 4. 朋友圈：同一数据模型支持日常帖子和 letter 展示

### 4.1 产品规则

帖子可以是文字、图片、周家明自由活动后想分享的东西，或像信一样排版的内容。`presentation = "letter"` 只决定展示样式；它仍是一条朋友圈帖子，使用同一作者、时间、附件、读取和评论机制。

不要恢复 Mariposa 已退役的 letter 数据域，不向 Mariposa 新增 letter 表或 letter 能力，不把每条信式帖子自动写成桶。是否 hold 成记忆，仍遵循现有主模型选择与 Mariposa 规则。

周家明醒来后可以不发帖。没有新帖、评论或作品是正常结果，不显示“未完成分享”，不自动补发，不定时催交，不用小模型检查“为什么今天没发”。

### 4.2 建议最小表

| 表 | 必要字段 | 约束 |
|---|---|---|
| `feed_posts` | `id`、`author_actor`、`presentation`、可空 `title`、`body`、`created_at`、`published_at`、`updated_at`、`revision`、可空 `deleted_at` | actor 仅双人；presentation 仅 `post`/`letter`；published_at 服务端确定 |
| `feed_post_assets` | `post_id`、`asset_id`、`position`、可空 `alt_text` | 文件不进入此表；同帖排序稳定，重复 asset 去重或明确拒绝 |
| `feed_comments` | `id`、`post_id`、`author_actor`、`body`、`created_at`、`updated_at`、`revision`、可空 `deleted_at` | 评论绑定真实帖子；第一版平铺按时间排列，不新增多层回复树 |

`deleted_at = null` 表示有效内容，非空表示已删除；无需再并行维护一套会互相矛盾的状态字段。为帖子/评论排序键建立组合索引，评论额外以 `post_id` 为索引前缀。content 自己的表之间启用外键并在本地事务中更新；评论外键不能配置成删除帖子时级联清空。`asset_id` 和 Mariposa 引用是跨服务 ID，不得伪造跨库 SQL 外键。

第一版评论支持文字即可；附件可随后复用同一媒体引用机制，不为当前请求再建一套上传。帖子必须至少有非空正文或一项附件。建议正文上限 40,000 字符、评论 10,000 字符、标题 200 字符，作为可配置限制；附件数量和类型沿用媒体规范。

正文按安全 Markdown 或普通文本显示；禁用原始 HTML。可显示分享链接，但不能执行其中代码，不能把链接自动当成附件持久保存。希望长期保存图片时先走媒体导入，再引用资产。

### 4.3 发帖、评论与删除

发帖流程为：认证并派生 actor → 校验文字/资产 → 取得资产引用保护 → content 事务保存正文与附件引用 → 返回已保存对象。只有得到保存成功结果，前端或模型才能称“已经发出”。

评论流程同样必须检查帖子存在且未删除；读取双方私密内容的权限不能由“只知道帖子 ID”取得。重复网络提交只能产生一条评论。

建议删除默认如下：

1. 删除自己的评论，立即移除可见正文；保留必要 ID/时间墓碑用于稳定翻页，界面可以显示“评论已删除”。
2. 删除自己的帖子，移除可见标题、正文和该帖附件关联；保留最小已删除标记。
3. 帖子已有他人的评论时，不级联删除评论。保留“原帖已删除”及既有评论，评论作者仍可删除自己的评论；不再接受新评论。
4. 无评论的已删帖子从常规列表隐藏；有仍可见评论的已删帖子保留最小占位。原帖删除不授予删除他人评论的权力。
5. 不因删除帖子或评论删除聊天原文、桶、我们的话、相册中仍引用的图片。

此处墓碑只需要支持引用、并发与幂等，不要求建立全文版本史或新的回收站系统。删除后不得把原正文继续从普通读取接口返回。

### 4.4 拟议 HTTP 面

| 方法与路径 | 用途 | 主要输入/返回 |
|---|---|---|
| `GET /api/v1/content/posts` | 双方私密帖子列表 | `cursor`、`limit`、可选 `presentation`；返回卡片及 `next_cursor` |
| `GET /api/v1/content/posts/{id}` | 帖子正文/已删占位 | 返回正文、真实作者、展示样式、资产 ID、时间和 revision；评论独立分页 |
| `POST /api/v1/content/posts` | 发帖 | 正文：`presentation`、`title?`、`body`、`asset_ids[]`；头：`Idempotency-Key` |
| `PUT /api/v1/content/posts/{id}` | 更新本人帖子 | 正文：可编辑字段、完整附件引用集合；头：`If-Match`、`Idempotency-Key` |
| `DELETE /api/v1/content/posts/{id}` | 删除本人帖子 | 头：`If-Match`、`Idempotency-Key`；保留他人评论 |
| `GET /api/v1/content/posts/{id}/comments` | 时间顺序评论列表 | 独立 `cursor`、`limit`，游标绑定该帖 |
| `POST /api/v1/content/posts/{id}/comments` | 添加评论 | 正文：`body`；头：`Idempotency-Key` |
| `PUT /api/v1/content/comments/{id}` | 更新本人评论 | 正文：`body`；头：`If-Match`、`Idempotency-Key` |
| `DELETE /api/v1/content/comments/{id}` | 删除本人评论 | 头：`If-Match`、`Idempotency-Key` |

所有公开请求体都没有可赋权的作者字段。后续相册、作品和未来留言的写接口也统一沿用第 3.2 节的 `If-Match` / `Idempotency-Key` 约定，不各自另选参数位置。

## 5. 三类相册：复用资产，只新增归档信息

| 类别 | 内容与字段 | 关联/搜索要求 |
|---|---|---|
| `chat_screenshots` 聊天截图 | 截图资产、可选说明 | 可关联 Mariposa 的一条或多条 `our_words`；沿用其专门搜索语义，不把截图 OCR 偷偷并入普通桶召回 |
| `important_photos` 重要照片 | 日常照片、重要图片、值得保存的生成图片 | 双方均可添加；使用已持久保存的 `asset_id`，可加说明和已有桶事件引用 |
| `stickers` 表情包 | 图片资产、可空含义文字、可选标签 | 含义可人工/由周家明编写并修改；从库中选择后仍走现有聊天附件发送能力 |

最小表为 `album_entries`：`id`、`kind`、`asset_id`、`added_by_actor`、`caption?`、`meaning?`、`created_at`、`updated_at`、`revision`。关联表 `album_entry_refs` 只保存 entry 与源对象稳定引用，不复制源正文。

同一资产可进入多个类别，也可同时出现在聊天、帖子或纪念作品。第一版同一 `(kind, asset_id)` 只保留一个归档记录；再次添加返回既有记录，不强行再复制文件。新增来源人可记录在操作记录中，但不能因此覆盖别人写的说明。

图片不要求先写含义才允许入库。表情包含义能表达你们自己的使用习惯；缺少含义时可继续展示/发送，不自动补成固定情绪。图像向量索引、生图供应商都是外部可替换能力；第一版可以先完成按含义/说明的文本搜索与人工选择，不把任何特定向量模型或生图模型作为相册启动前提。

截图关联新增前，est 验证对应 `our_words` 存在且 actor 可访问。请求带关联引用时，任一引用校验失败则本次归档写入失败，不能静默丢弃关联后返回成功；先前已经上传的图片资产不因此删除，临时保护按媒体流程处理。双方可以随后明确提交不含关联的归档请求，先存入截图相册，再在源服务可用时补关联。

截图搜索的闭环为：走 Mariposa 既有“我们的话”专道 → 得到真实 `our_words` ID → 用该引用反查 content 的截图归档。为 `album_entry_refs` 建立 `(service, kind, source_id, entry_id)` 索引，既有相册列表接口接受成组提供的 `source_service`、`source_kind`、`source_id` 精确筛选；游标绑定这三个筛选值。不能仅保存关联却没有反查入口，也不复制话的正文建立第二个索引正本。

拟议新增接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/content/albums/{kind}/entries` | 按类别分页，支持说明/含义文本查询及 `source_service` + `source_kind` + `source_id` 精确反查；游标绑定 kind 与全部查询条件 |
| `POST /api/v1/content/albums/{kind}/entries` | 添加已存在的资产及可选说明、含义、关联 |
| `PUT /api/v1/content/album-entries/{id}` | 更新元数据/关联，校验 revision；替换资产时遵守引用保护 |
| `DELETE /api/v1/content/album-entries/{id}` | 移除该归档及它的关联；不是删除外部原文或全局原文件 |

周家明“独立上传重要照片”的完整链必须是：先通过既有媒体上传/导入能力得到真实持久资产，再调用相册添加。输入可以来自生成结果、允许读取的现有文件或下载链接；最终归档对象是图片文件的资产 ID，不能只把会过期的外链当作“照片已保存”。具体上传、`media_import`、`chat_send_attachment` 合同以媒体文件为准。

## 6. 纪念空间：图标、可选作品、已有事件

### 6.1 明确不生成创作义务

纪念记录只在明确创建操作时存在。写一只桶不会自动创建待做图标、待做动画或欠作品任务。周家明可以愿意做、以后做、先只做图标或一直不做；没有作品不计失败。

最小 `creations` 表：

| 字段 | 规则 |
|---|---|
| `id`、`creator_actor` | 稳定 ID；创建者可信派生 |
| `title?` | 可选作品名；不替代桶标题 |
| `bucket_ref` | 必填，指向已有 Mariposa 桶；创建/换绑时验证 |
| `icon_asset_id` | 必填，纪念空间入口图标；可为经媒体规范处理的图片/SVG |
| `work_asset_id?` | 可空；没有作品也能正常打开桶 |
| `work_kind?` | 有作品时明确 image/video/html 等支持类型；不靠扩展名猜执行方式 |
| `created_at`、`updated_at`、`revision` | 作品时间；不是事件发生日期 |

`work_asset_id` 与 `work_kind` 必须同时为空或同时有效。图标和作品各自验证用途/MIME；不允许把未知可执行文件按图片展示。没有作品是有效状态，不新增待完成字段。

实际事件日期每次通过桶引用读取，不能让作品的可编辑日期反写 Mariposa。若为月视图建立可重建投影，要标识源和更新时间，发生日期改正后能重新读取；不增加第二个可独立编辑的事件日期正本。

### 6.2 点击行为

- 无作品：点击图标直接进入关联桶。
- 有作品：点击图标打开作品；看完后显示明显的“回到这件事”入口，跳转关联桶。
- 作品播放过程中保留随时返回/去事件的入口，不强制看完。
- 无法播放：展示可解释的失败状态和可用的桶入口；不丢掉整个纪念记录。
- 后来补作品：更新原记录的作品引用，不另写桶，不把中秋约会挪到作品制作日。
- 桶删除：作品仍可查看，桶入口标记目标不存在；源服务离线时标记暂时不可达。

拟议路由为 `GET /api/v1/content/creations`、`GET /api/v1/content/creations/{id}`、`POST /api/v1/content/creations`、`PUT /api/v1/content/creations/{id}`、`DELETE /api/v1/content/creations/{id}`，沿用身份、幂等、revision 和分页合同。

### 6.3 可执行小作品的展示边界

普通图片与视频走已有媒体查看器。HTML/Canvas 小作品必须使用受限制的展示容器；不把作者上传的脚本直接插入 est 主页面。

第一版 HTML 作品采用自包含单文件，可包含内联样式、SVG 和 Canvas 逻辑；不要求在线安装依赖或由 content 执行构建脚本。需要外部资源的作品暂不作为完整支持的格式，不能通过开放任意外网权限来补救。

模型保存 SVG/HTML 文件时使用媒体规范的 `creation_save_artifact({format, content, client_operation_id})`，由 est 安全落为资产后返回 `asset_id`，再创建或更新纪念记录。保存工具不执行作品代码；content 不重复实现该保存入口。

第一版要求：iframe sandbox 只授予展示必需权限；允许脚本时不同时给予 same-origin、顶层导航、表单、弹窗等无关权限；资源策略默认禁止任意外网请求。作品不能读取 est 登录凭据、调用内容写入接口或直接操作聊天。若资产为 SVG，图标采用安全图片方式显示，不能直接把未处理 SVG 注入 DOM。

“回到事件”链接由宿主 UI 根据已验证 `bucket_ref` 生成。作品若需要通知播放完成，只接受预定义完成消息；校验 `event.source` 与该 iframe、当前实例标记和消息类型，不采用作品传来的任意跳转 URL。sandbox 的 opaque origin 不能被误当成普通同源来源校验。

没有 completion 事件的小作品仍保留宿主入口。不要为所有作品强制增加单独播放器服务、构建服务或游戏服务。

## 7. 日历：读聚合，不成为新的事实数据库

### 7.1 哪些日期显示什么

| 来源 | 日历使用的日期 | 详情与跳转 |
|---|---|---|
| 聊天 | 消息真实发生时间换算为北京时间日期 | 当天完整聊天、定位指定消息 |
| Mariposa 桶 | **事件实际发生日期** | 标题列表 → 桶详情 → 相关原文 |
| Mariposa 计划 | 原服务定义的安排日/到期日 | 原计划详情和状态；编辑回原服务 |
| Superposition | **现有 special_dates 所代表的重要日期** | “今天可以拆星”的提示与安全进入流程的入口 |
| 提醒 | 用户/模型明确设置的到期时间 | 提醒状态及相关对象 |
| 未来留言 | est 关联任务明确指定的展示/投递日和时间 | content 留言正文与 est 任务状态的聚合；不以留言创建日代替 |
| 纪念作品 | 关联桶的实际发生日期 | 图标/作品与原桶 |

以下情况不产生额外日期标记：今天写入一颗星；今天为旧桶补写一件作品；今天导入一张没有事件关联的普通照片。朋友圈发帖和相册上传也不自动扩张成本轮日历的新事件类型。

无明确发生日期的旧桶不能用写入日期代替，也不能塞到今天。可以通过源服务已有未标日期入口处理；源服务未提供时列为待核对能力，不杜撰日期。多日事件只按源合同的明确日期范围显示；不要自行推导新的日历语义。

一次中秋约会使用那一次真实公历日期。每年中秋提醒必须来自源服务明确的农历/节日规则；不得把某一年的公历日期复制为“每年中秋”。第一版不替星星服务另建一套节日推算器。

### 7.2 月概要与日详情

月份首次加载只查询哪些日期有内容、各类型数量及来源状态，不下载整月桶正文或聊天原文。选中一天才读取该日各来源的分页详情。

拟议新增聚合面：

| 接口 | 输入 | 返回 |
|---|---|---|
| `GET /api/v1/calendar/month` | `month=YYYY-MM` | 每日各来源的数量/标记，以及每个来源 `ready`/`disabled`/`unavailable` 状态 |
| `GET /api/v1/calendar/day` | `date=YYYY-MM-DD` | 该日轻量概要和各来源入口，不一次返回全部原文 |
| `GET /api/v1/calendar/day/items` | `date`、`source`、`cursor?`、`limit?` | 指定来源的稳定分页；不同来源分别翻页 |

`source` 只能取适配器注册集合。各来源分别分页可避免新增复杂的跨服务统一游标。源服务已有游标时适配器包装并绑定查询；源服务只有有限结果却提示有更多时，不能把首批结果标成“全部”。

建议读适配结果：

```json
{
  "date": "2026-10-11",
  "timezone": "Asia/Shanghai",
  "source": "memory",
  "status": "ready",
  "items": [
    {
      "source_ref": {"service": "mariposa", "kind": "bucket", "id": "bucket-id"},
      "event_date": "2026-10-11",
      "title": "事件标题",
      "target": {"kind": "bucket_detail", "id": "bucket-id"}
    }
  ],
  "next_cursor": null,
  "complete": true
}
```

这是 est 自己的拟议展示 DTO，不能据此宣称 Mariposa 返回完全相同的字段。`target` 使用允许的类型及稳定 ID，由前端生成内部跳转，不透传任意脚本 URL。

源服务没有廉价月计数接口时，优先复用已有有界列表/批量读；确需新增时在联合改造清单里声明读合同。首版可以显示“有内容/数量待加载”，不得伪造精确数量。不要为了月计数启动额外数据库同步工程。

### 7.3 当天聊天与相关原文必须分开

北京时间一天查询为半开区间：`[当天 00:00, 次日 00:00)`。例如 2026-10-11 对应 UTC `[2026-10-10T16:00:00Z, 2026-10-11T16:00:00Z)`；不要使用 `23:59:59` 作为上界。

桶详情至少保留两个有区别的入口：

1. **相关原文**：由桶真实绑定关系读取的那段或多段原文。
2. **当天完整聊天**：该事件日期的全部已保存聊天，包括未 hold 的闲聊。

绑定原文可能跨日期，不能强行裁成桶日期当天。当天聊天也不要求与某只桶绑定。日期拆窗、64k 换窗、缓存过期、没有入选新窗口都不改变原文保留规则。这里只新增只读适配及定位，不迁移既有原文权威存储。

### 7.4 跨源失败与写后刷新

一个来源不可达时，其余来源继续显示。失败来源显示“暂时不可用”，不能返回零条并假装没有记录。月聚合/概要允许整体 HTTP 200 并带明确部分失败；单源详情无法读取时返回相应 503。无权限与源服务离线应分别处理，不在错误正文泄漏凭据或本地路径。

用户在本次操作中新增/编辑/删除内容后，前端刷新受影响日期和列表即可。第一版不需要跨服务消息总线。再次打开日历也要读取当前源状态，不能永久展示上次进入页面时的快照。

## 8. 计划、未来留言、提醒和星星的执行职责

Mariposa 计划是唯一事项正本。日历的编辑操作调用真实计划服务，成功后刷新；不能在 est/content 保存一份单独完成状态。est 的提醒记录只保存计划引用、触发时间、投递状态和幂等键。计划完成/取消后是否还提醒，按既定提醒规则校验，不把调度成功等同于计划完成。

未来留言正文归 content，调度/投递归 est，具体合同见下节。本轮 feed 的 `letter` 是已经发布帖子的展示形式，不自动具有定时投递或星星解锁功能。未来留言也不复活 Mariposa letter 域。以后若明确要定时发朋友圈，可以复用 est 调度器调用同一发帖入口，但不作为这轮默认新增范围。

只展示预先写好的提醒/留言不需要调用模型。如果届时需要周家明重新决定内容，那次模型活动走主包的自主活动调度与预算，不能躲在 content 任务里绕开限频。

星星必须遵守以下只读边界：

- 月历、日历详情、提醒预览只读取重要日期及明确允许的状态。
- 不以“预加载”“取得预览内容”为名调用取下一颗星、确认拆星、消费会话等写接口。
- 当天提醒只说明可以进入既有拆星流程，不能把提醒投递标成星星已拆。
- 用户或周家明进入星星流程后，继续遵守原服务已有邀请、确认和拆星规则。
- 星星服务的完整合同尚未读到时，适配器先关闭相关动作，保留待接接口；不要制作一个行为相近但状态不同的复制实现。

### 8.1 未来留言的最小数据与 CRUD

同一 content 数据库新增 `future_notes`：`id`、`author_actor`、可空 `title`、`body`、`created_at`、`updated_at`、`revision`、可空 `deleted_at`。附件使用 `future_note_assets(note_id, asset_id, position)`，沿用同一资产验证、pin 和引用回收；不增加字节文件副本。正文必须非空或有有效附件。

这里不保存可独立编辑的 `deliver_at`、投递完成状态或循环规则。目标时间、启用/暂停、执行状态都取自 est 已有或第 04 章新增的 `background_tasks` / `background_runs` 及现有消息投递记录。源引用为 `{service: "content", kind: "future_note", id: note_id}`；任务身份和会话由宿主派生，不能借读取对方留言的权限把它改成自己的发言。

| 方法与路径 | 用途 | 输入/输出边界 |
|---|---|---|
| `GET /api/v1/content/future-notes` | 双人私密留言列表 | 默认 20、最多 100，按 `(created_at DESC, id DESC)` 稳定分页 |
| `GET /api/v1/content/future-notes/{id}` | 正文及当前版本 | 返回 author、body、asset IDs、revision/ETag；任务状态由 est 读聚合 |
| `POST /api/v1/content/future-notes` | 创建本人留言正文 | `title?`、`body`、`asset_ids[]`；`Idempotency-Key`；成功仅代表正文已保存 |
| `PUT /api/v1/content/future-notes/{id}` | 修改本人源留言 | 正文与完整附件集合；`If-Match`、`Idempotency-Key` |
| `DELETE /api/v1/content/future-notes/{id}` | 删除本人源留言并阻止尚未开始的关联投递 | `If-Match`、`Idempotency-Key`；返回是否已有投递提交，不能伪报撤回历史消息 |

前端“保存并安排”可以依次调用正文创建和现有 background task 创建；第二步失败时明确显示“留言已保存，尚未安排”，允许复用同一操作键重试安排，不能显示“提醒设置成功”。聊天工具同理，正文工具返回 `note_id` 后，有限的 `background_task_create` / `background_task_update` 负责指定时间或启停。

默认时间取 contracts/policy-defaults.json 的 background.reminders.default_local_time，界面必须显示；background task API 仍要求明确 scheduled_at。第一版留言投递使用 `kind=reminder`、`schedule_kind=once`，同一留言最多一条启用且未完成的投递任务，由任务服务在事务中保证。日期没有时间时按前端明确显示的配置默认时间安排，不让程序偷偷选择当前时间。单独保存正文不自动开始投递，不凭日期字段复制周期任务；已经完成后再次发送必须是新的明确安排。

### 8.2 到期读取、冻结版本和幂等消息

到期执行仍由第 04 章的一份调度器领取。先检查普通提醒总开关、任务开关、task revision、occurrence、可信作者及现有会话权限，再通过 content 读适配取得当前未删除留言。不能调用模型重写这段留言。

投递调用既有消息保存/展示层，不调用“收到一条新用户输入就启动模型”的入口。即使留言作者为 `qiaosheng`，也不能因消息角色而自动触发额外回复；需要届时模型思考的任务必须另外经过第 04 章自主活动门控。

读取失败、正文/附件不完整或 content 离线时，本次投递不得落空消息、不得猜正文、不得把最终状态写成成功。记录真实失败/暂不可达，并按第 04 章已有宽限期和恢复规则有界处理；错过后保留可见状态，不无限补发。

正文编辑/删除、关联任务停止和该留言的最终投递，必须走宿主同一个按 note ID 串行的短临界区，并复用任务的持久 revision/fence。est 已有单实例要求继续适用；这不是再部署一个锁服务。不要在锁内等待模型或外部付费操作。

编辑/删除先核对当前 note 的作者、存在状态与 `If-Match`。版本冲突或无权操作时不得先取消任务、释放资产或改正文。客户端超时后，先解析同一幂等操作的已知结果，再判断是否需要重新校验版本；不能把已经成功的删除重试误报成一项新操作。

投递前读取到 revision R 后，在最后一次任务 fence 校验与现有幂等投递入口之间冻结：note ID、R、作者、正文、附件引用、目标会话及 occurrence。冻结内容进入现有受保护消息/outbox 记录，保持为该次投递证据；不新增第二份聊天表或新投递 outbox。稳定投递 operation ID 由既有 occurrence 派生，不能因为重试或后来读取到不同 note revision 而更换 ID。

只有现有投递层确认提交，才显示准确的“已保存到聊天/已投递”状态；若只有 outbox 接受而未确认最终落点，就显示待投递，不能提前写“已送达”，也不能推定手机推送已收到。网络断开后用同一 operation ID 核对收据/恢复，不能生成第二条消息。最终消息保留真实作者、来源 note ID 与冻结 revision；江乔生的源留言不能冒充周家明的回复。以后编辑源留言不改写已经发送的消息。未来另一次明确安排可以读取新版源留言，旧消息始终对应原冻结版本。

### 8.3 停止、删除与正在投递的竞态

按现有投递层真正的提交点决定顺序，不能靠前端按钮点击时间猜测谁先完成：

- **停止或删除先取得 fence，投递尚未不可撤销提交**：取消后续领取/可取消投递；最终提交再次检查 fence，因此不再产生消息。随后才完成 content 源留言删除及它自己的资产解绑。取消成功但 content 删除失败时，报告“投递已停止、留言删除未完成”，用同 key 恢复，不伪报全部成功。
- **消息提交先完成**：后来的停止/删除只能阻止未来动作；返回 `already_committed` 与允许读取的 message ID。可以继续删除源留言，但不撤回或改写已发消息，不释放该消息仍需要的媒体引用。
- **投递结果未知**：保留同一 operation ID 核实和资产保护，显示待核实；不一面声称取消成功，一面重新发起另一条消息。
- **编辑发生在冻结前**：本次投递可读取编辑后的最新有效版本；编辑发生在冻结后，本次投递保持已冻结版本。响应应明确现有 occurrence 是否已经冻结/提交，避免把源文稿修改显示成改好了已发消息。

删除源留言前，宿主先取消其未完成关联任务并 fence 正在领取的 occurrence。content 不反调 est 来完成取消，所有公开删除由 est adapter 协调；重启恢复沿现有任务和消息状态，不让已删 note 的孤儿任务继续发出。仅删除源留言不删除聊天历史。

## 9. 内容写入与资产引用的一致性

资产文件及引用保护统一归 est。content 不保存 base64、二进制、独立下载缓存或另一套永久图片 URL，也不自主删除媒体文件。

est 的 host content adapter 执行同一写操作：

1. 验证 actor 和目标操作，按媒体规范校验所有新增 `asset_id`。
2. 持久记录操作幂等键和所需引用变更意图，先为新增引用建立临时保护 pin。
3. 带内部凭据和可信 actor 调用 content，正文及其 `asset_id` 集合在 content 本地事务中一起提交。
4. content 成功后，宿主把已提交对象与引用确认关联，释放多余/旧引用的 pin；完成 outbox 记录。
5. content 明确失败时回收该操作的多余临时保护；状态不明时保守保留，不把可能已经发布的媒体交给 GC。
6. 进程重启或返回丢失时，根据持久意图用同一幂等键恢复结果，低频本地 reconcile 收敛引用状态；不调用模型。

这是一份轻量 outbox/补偿流程，不是分布式事务平台。无需两阶段提交、独立队列或新的协调服务。pin、引用账本和 outbox 的具体表结构复用媒体规范，不在 content 再建相同账本。

更新附件须先保护新增引用，待正文成功更新后再释放被移除引用。删除帖子、相册归档或作品时，仅解除该内容对象自己的关联；原文件能否删除由资产服务检查聊天、其他内容、有效任务和保护记录。若引用回收失败，宁可短暂保留文件，也不能出现已发布内容引用的文件被误删。

## 10. 轻量工具面：让周家明可以使用，同一份业务实现

以下是拟议宿主工具名；GLM 可按现有能力注册规范进行明确映射，不再发明平行业务实现。前端走 HTTP，模型调用工具，最终调用的是同一个 content 业务服务。

| 工具语义/建议名 | 最小作用 |
|---|---|
| `content_posts_list`、`content_post_get` | 分页看帖子、按需读取正文；post_get 不把一页评论冒充全部 |
| `content_comments_list` | 对应 `GET /api/v1/content/posts/{id}/comments`，携带 post ID、cursor、limit 独立分页 |
| `content_post_create` | 发普通帖或 letter 样式帖，支持既有资产引用 |
| `content_post_update`、`content_post_delete` | 修改/删除本人帖子，revision 和幂等校验 |
| `content_comment_create`、`content_comment_update`、`content_comment_delete` | 评论及管理本人评论 |
| `content_album_list`、`content_album_add`、`content_album_update`、`content_album_remove` | 浏览及维护三类共享归档；list 支持经过校验的源引用反查 |
| `content_creations_list`、`content_creation_get`、`content_creation_create`、`content_creation_update`、`content_creation_delete` | 自愿创建/后补/维护纪念记录；get 对应作品详情路由 |
| `content_future_notes_list`、`content_future_note_get`、`content_future_note_create`、`content_future_note_update`、`content_future_note_delete` | 留言正文的有限读写；工具不拥有独立调度循环，安排时间仍用 background task 工具 |

不向模型开放原始 content SQL、任意 actor 写入或任意媒体物理删除。使用工具不要求每次先建一个新的 MCP 服务器；沿现有宿主工具注册 → HTTP 适配即可。若以后确需供其他客户端使用 MCP，再为同一业务服务添加薄协议入口，不改变数据正本。

oído、扎西德勒、X、小红书继续作为外部能力；本文件不实现其浏览器、社交业务或听觉管线。周家明从这些能力取得可分享结果后，可自主决定调用发帖工具。工具调用失败不自动改成向另一个朋友圈发帖。

## 11. 游戏厅、情绪维度、生图和图检索

- **游戏厅**：第一版仅保留可选入口与空状态。若以后有小游戏，可复用已受限制的小作品查看器；不预建积分、排行榜、匹配、实时服务器和每日任务。
- **情绪**：只读取 Mariposa 已明确可展示的心情标签及其关联桶/记录时间。维度架构待定，不自动生成数值、映射坐标轴或推导“周家明现在的心情”；自由心情文字继续遵守原有读取/窗口边界，不因新页面而扩权。
- **生图**：外部可替换工具返回图片后，先进入 est 资产服务，再按明确操作发送聊天或加入相册/作品。无需每个图标都调用付费生图模型。
- **图检索**：先保证文本含义搜索与人工选择可用；外部图像向量服务可以后接。不能将某个尚未核验的模型能力、部署条件或性能写成相册必需依赖。

## 12. 错误与恢复合同

新增 HTTP 面采用全包统一错误包，至少能表达以下语义；若总包已经定义同义错误码，统一复用，不重复造词。

| 状态 | 建议错误码 | 行为 |
|---|---|---|
| 400 | `INVALID_ARGUMENT` / `INVALID_CURSOR` | 日期、类别、限额、游标与当前资源不匹配；返回可修正字段，不执行写入 |
| 401 | `UNAUTHENTICATED` | 会话或内部服务凭据缺失/失效 |
| 403 | `FORBIDDEN` | 非双人读取、编辑他人帖子/评论/作品、试图伪造作者 |
| 404 | `NOT_FOUND` | 内容或明确查询的源对象已不存在；不能将上游离线映射为 404 |
| 409 | `REVISION_CONFLICT` | 当前版本与预期不符，返回允许读取的当前 revision |
| 409 | `IDEMPOTENCY_CONFLICT` | 同幂等键请求不同；不创建第二条对象 |
| 409 | `PARENT_DELETED` | 对已删帖子评论或编辑已删对象 |
| 422 | `INVALID_ASSET` / `UNSUPPORTED_MEDIA` / `INVALID_REFERENCE` | 资产不可用、格式不支持、关联种类不允许等；细节服从媒体规范 |
| 503 | `CONTENT_UNAVAILABLE` / `SOURCE_UNAVAILABLE` | 对应服务不可达；读聚合可保留其他源结果 |

安全拒绝、对象已删除、版本冲突和无内容不是重试型故障。网络重试必须有上限且复用同一幂等键。不要通过重试风暴“等上游恢复”，不要把失败发布展示为成功后后台无限补发。

## 13. 必须证明的验收结果

以下覆盖真实剩余风险，不要求为每个纯展示字段逐个写镜像测试。可合并相关场景，但报告要说明实际输入、结果和失败分支证据。

### A. 部署、身份与发布

1. 同一前端通过 est 认证读取内容；content 不直接暴露公网。content 停止后，聊天发送仍可用。
2. 江乔生通过前端发帖/评论，作者为 `qiaosheng`；周家明通过宿主工具发帖/评论，作者为 `jiaming`。浏览器/工具自填另一个 actor 不能改变作者。
3. 双方都能看双方的普通帖和 letter 样式帖并发表评论；未认证和第三 actor 不能访问。letter 不触发 Mariposa letter 表/旧能力或自动 hold。
4. 更新/删除本人内容成功；改删另一人的帖子或评论被拒。维护上下文不能悄悄冒名。
5. 同一发帖或评论请求重复提交、响应丢失后重试，只产生一份内容。同 key 改正文被拒；同 revision 并发更新最多一方成功。
6. 删除本人帖子后，他人的评论不被级联删除，新增评论被拒；普通接口不再返回已删除正文。

### B. 分页、媒体与恢复

7. 大于一页且多个时间戳相同的帖子/评论分页无重复、无遗漏；翻页期间新增和编辑不打乱既有遍历。不同帖子之间交换评论游标必须失败。
8. 重要照片从真实文件或允许的链接导入得到资产，随后由周家明工具归档；刷新、重新登录、重启后仍能读取图片，不依赖临时生成链接。
9. 同一图片被聊天、帖子和相册引用；删除任意一处不会破坏其他处。截图解绑/删除不影响 `our_words` 或原文。
10. 在 pin 后/content 提交后/引用确认前分别中断一次，重启后可恢复同一对象并收敛引用；状态不明时媒体不会被 GC 误删。
11. 修改附件先保护新增引用；失败不会让旧帖子失去原图。验证 content 没有同步回调 est 造成的等待链。

### C. 日历与星星

12. 同一事件晚写桶、再晚补作品，桶与作品仍显示在源服务实际事件日期；未知日期不回退成创建日。
13. 测试北京时间午夜边界和带毫秒消息：当天 00:00 包含，次日 00:00 排除；按天查询涵盖多次内部换窗。
14. 桶的相关原文可包含跨天片段；当天完整聊天入口包含未 hold 闲聊。两者不错误互换。
15. 日期内容超过单页上限，日详情能继续读，不能把 `has_more` 当成“当天全部”。源服务离线显示不可用而非零条。
16. 今天写星星不产生今日拆星标记；只有源重要日期产生标记。仅查看月历、日详情、提醒预览，星星剩余数量、取星状态、确认状态不得变化。
17. 编辑计划回到 Mariposa 正本；提醒的投递状态不能更改计划完成状态。预写提醒准时投递无需额外模型调用。

### D. 自愿作品与可选功能

18. 新增桶不会产生待创作任务。只有图标的纪念记录直接开桶；后来添加动画仍绑定同一桶，播放结束出现事件入口且允许随时返回。
19. 小作品脚本不能读取 est 会话、触发发帖/删帖或顶层跳转；宿主不接受作品提供的任意跳转 URL。
20. 没有新帖/新作品的自主活动能正常结束；content 不自行定时调用模型。空游戏厅正常展示；没有心情记录时不补中性值，不把历史标签冒充当前情绪。

### E. 未来留言与合同完整性

21. 未来留言正文只在 content 管理，est 任务只保留引用和必要投递信息；创建正文但安排失败时不能显示已设好。到期 content 不可达时不发空消息、不调用模型补文。
22. 冻结前编辑发送新版；冻结后编辑不改已冻结/已发消息。重复回调、发送收据丢失后同 operation ID 恢复，只有一条最终消息且来源 revision 可查。
23. 分别验证停止/删除先于提交、提交先于停止/删除、结果未知三种竞态；只报告已证实的取消/提交结果，源留言删除不破坏已发消息及其附件。
24. 所有 HTTP 写入使用 `Idempotency-Key`，更新/删除还使用 `If-Match`；工具参数映射一致。伪造 body/query 控制字段不能绕开头部校验；content_comments_list 可以翻完多页评论，content_creation_get 读取到完整作品引用。
25. “我们的话”专道返回的真实 ID 能反查绑定截图，游标不能换 ID 继续使用。日历/搜索/作品预取和播放不触发明确打开确认；真正打开桶才走既有确认。帖子按 published_at 排序，后来编辑不重排，未来留言创建时间不混入帖子发表排序。
